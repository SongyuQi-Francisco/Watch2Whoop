> 状态：规划稿，2026-11-14，等负责人看完后再开始第一个 demo。这份文档只做规划：没有代码、没有正式设计稿，屏幕用文字线框说明。

## 0. 摘要

- **定位**：手表是「手腕上的记录键」，手机是「仪表盘」。手表只做三件事：训练时记一组、张嘴记一餐或问一句、抬腕看一眼今天的状态。
- **第一个 demo 建议**：只做「训练中记组」：开始训练 → 每组点一下（或双指互点两下）→ 自动进组间休息（倒计时、实时心率、到点震动）→ 结束后手机上看到这次训练。不含语音、不含表盘小组件。
- **语音**：手表上没有 iPhone 那套本机语音识别框架（第 4.3 节）。推荐把录音发给服务器已有的 `/v1/assistant/transcribe`，系统听写做兜底。
- **数据走向**：手表不直接写服务器的训练记录。它把「记了一组」这类事件交给手机，由手机并进本地库、经现有离线队列上传。手机不在身边时，事件先存在手表里，之后补交。
- **训练质量**：手表上只摆事实（完成几组、比上次多多少、组间心率降了多少、休息了多久），不做一个「质量分」。理由见第 2.1 节。
- 要负责人决定的 9 个问题在第 6 节，每个都有推荐。

## 1. 定位和分工

### 1.1 一句话

**是什么**：训练和吃饭的当下，用一次点按或一句话把事情记下来，并让 Jarvis 听得见；顺带在表盘上给出今天的恢复和负荷。

**不是什么**：不是手机 app 的缩小版。不看趋势，不翻历史，不编辑计划，不管理账号，不展示长文字。

负责人的设想（手机偏展示、手表偏快速记录和调用 AI、交互靠语音）我基本同意，补两点修正：

1. **训练中的主交互是点按和手势，不是语音**。健身房很吵，做组间隙喘着气，周围有人，说话既不准也不自在。记一组要做到「不看也能点中」：整屏一个大按钮，或者双指互点两下（Double Tap）。语音留给饮食和提问。
2. **手表不只是输入，还是传感器**。手表上跑训练会话可以拿到实时心率，这是手机做不到的。「训练质量」的原始材料（组间心率、休息时长）只有手表能采到。

### 1.2 分工表

| 功能 | 手机 | 手表 | 理由 |
|---|---|---|---|
| 恢复 / 睡眠 / 负荷分数 | 完整仪表 + 展开层 | 一眼（一个表盘 + 两个读数）、表盘小组件 | 手表只回答「今天能不能练」，原因留给手机 |
| 趋势、报告、身体年龄、睡眠阶段图 | 有 | 不做 | 要读图、要比较，小屏做不好 |
| 今天的训练：记组 | 有（完整，可改任意一组） | **主场**：当前这一组、组间休息 | 训练时手机常在柜子里或地上，手腕一直在 |
| 训练中的实时心率、组间心率 | 只在手表镜像过来时显示（后期） | **只有手表能采** | 传感器在手表上 |
| 训练计划：换动作、换分化、动作库、动作示范 | 有 | 不做（只读当前和下一个动作的名字） | 要搜索、要看图，属于训练前的准备 |
| 补记训练（有氧 / 球类） | 有（表单） | 语音一句话（经 Jarvis） | 手表不放表单 |
| 饮食：语音记一餐 | 有 | **有**（按住说话） | 一句话能说清，适合手腕 |
| 饮食：拍照记餐 | 有 | 不做 | 手表没有相机 |
| 饮食：快记模板、喝水 | 有 | 有（最多 4 个模板 + 喝水） | 一次点按，不依赖 AI |
| 饮食：改克数、看营养素、食谱、采购 | 有 | 不做 | 编辑类 |
| 问 Jarvis | 完整对话、卡片、历史 | 一问一答，回答是一张卡 + 最多两行字 | 长回答转到手机继续 |
| 日记、补剂打卡 | 有 | 第 3 期再评估（通知上直接打卡） | 不是负责人点名的场景，先不占位置 |
| 圈子 | 有（顶层入口） | 不做页面；别人的提醒走系统通知 | 圈子是社交浏览，属于手机。它仍是手机端的核心功能，这里不改变 |
| 同步中心、健康档案、AI 设置、账号 | 有 | 不做；手表只显示「已连接 / 去手机上登录」 | 设置类一律在手机 |
| HealthKit 数据同步 | 手机负责（现有同步引擎） | 不参与 | 手表的健康数据本来就会到手机的 HealthKit |

## 2. 核心场景（按优先级）

每个场景写：怎么触发、最少几步、屏幕上有什么、语音 / 点按 / 表冠 / 触感各管什么。

### 2.1 训练中记组（P0，第一个 demo）

**触发**（任选其一）：表盘小组件「开始训练」；Smart Stack 在计划的训练时间前后把它顶上来（第 3 期）；打开 app，今天有计划时首屏就是「开始」。

**最少步数**：开始训练 1 次点按；之后**每组 1 次点按**（或 1 次 Double Tap，不用碰屏幕）；结束 2 次点按（结束 → 确认）。

**屏幕**（三个状态，同一个页面里切换，不是三层导航）：

```
 做组中                      组间休息                    训练结束
┌───────────────┐          ┌───────────────┐          ┌───────────────┐
│ 卧推     2/4  │          │ 休息          │          │ 18/18 组      │
│               │          │    ╭─────╮    │          │               │
│   60 kg × 8   │          │    │ 1:12│    │          │ 52 分   6,480 │
│               │          │    ╰─────╯    │          │        kg     │
│ ♥ 132         │          │ ♥ 118  ↓14    │          │ ♥ 均 121      │
│ ┌───────────┐ │          │ 下一组 60 × 8 │          │ ┌───────────┐ │
│ │   完成    │ │          │ ┌───────────┐ │          │ │   完成    │ │
│ └───────────┘ │          │ │   跳过    │ │          │ └───────────┘ │
└───────────────┘          └───────────────┘          └───────────────┘
```

- **做组中**：动作短名 + 第几组 / 共几组；这一组的重量 × 次数（来自计划的推荐值，后端已有：`GET /training/session` 的 `target`）；实时心率；一个占满下半屏的「完成」。
- **组间休息**：倒计时环（时长取计划里这个动作的休息秒数，没有就用默认值）；实时心率和「比这组结束时降了多少」；下一组的重量 × 次数。倒计时到了震动一次，自动回到「做组中」。
- **训练结束**：完成组数 / 计划组数、用时、总重量、平均心率，四个数，没有句子。

**各输入方式的作用**

| 方式 | 作用 |
|---|---|
| 点按 | 「完成」记一组；「跳过」提前结束休息；点重量或次数让它进入可调状态 |
| Double Tap（双指互点两下） | 等于点主按钮：做组中 = 记一组，休息中 = 跳过。手上有汗、戴手套、握着杠铃时不用碰屏幕（待验证：第 4.10 节 V5） |
| 表冠 | 调当前选中的数：重量每格 2.5 kg（哑铃 / 器械的步长取动作的设置），次数每格 1。默认选中的是次数，因为实际做的次数最常和计划不同 |
| 左右滑 | 上一个 / 下一个动作（这一屏唯一的横滑含义）。不按计划顺序练时用 |
| 触感 | 记一组：成功震动；休息结束：提醒震动；心率回落到下面说的线：轻震一次（可关） |
| 语音 | 这个场景**不用**。例外：按住屏幕说「换成哑铃卧推」「这组 62.5 公斤 6 个」，交给 Jarvis 改（第 2 期，和 2.3 是同一个入口） |

**改错**：刚记的一组在休息屏上可以用表冠改重量 / 次数（它还没交出去，属于本机修改，不用确认）。删除已记的一组要确认（产品规则：只有删除 / 撤销要确认），入口在休息屏长按。更复杂的修改回手机做。

**RIR（还能做几个）**：后端的逐组记录有 `rir` 字段，推荐重量也用它。手表上默认**不问**：每组多一步会让「一组一点」变成「一组两点」。推荐做法：只在每个动作的**最后一组**休息屏上出现一行「还能做 0 / 1 / 2 / 3+」，表冠选，不选就留空。这是第 6 节的问题 Q5。

**训练质量怎么表达**

「质量」容易被做成一个 0–100 的分数，但现在没有可靠的依据把重量、次数、心率、休息合成一个数，合出来也说不清它意味着什么。推荐分两层：

- **手表上（训练中）**：只给能立刻用上的事实，每个都是「数 + 方向」：

  | 看什么 | 怎么显示 | 数据从哪来 |
  |---|---|---|
  | 完成度 | 第几组 / 共几组；结束屏 18/18 | 计划（已有） |
  | 比上次 | 这组的重量 × 次数旁边一个带符号的小数：`+2.5 kg` 或 `+1 次` | 上次记录（`GET /training/session` 的卡片里已有「上次」） |
  | 组间心率恢复 | 休息屏的 `↓14`：这组结束时的心率 − 现在的心率 | 手表实时心率（手表本地算，不用后端） |
  | 可以开始下一组 | 心率回落到「这次训练的静息段 + 一个比例」时轻震。阈值放在参数文件里并写明出处；**第 1 期不做**，先只用倒计时 | 需新增（规则 + 参数） |
  | 休息时长 | 倒计时环，超时后环变成正计时 | 计划的休息秒数（已有） |

- **手机上（训练后）**：这次训练的负荷、五区分钟、训练后 1 分钟心率恢复（后端已有：`workouts` 表的 TRIMP 和分区、`workout_hrr`）；每个动作的估算 1RM 变化（已有：`training/loads.py`）；**新增的是逐组的心率和休息时长**（需新增：见第 4.8 节），用来画「每组心率峰值 → 组间回落」这条线。
- **是否做一个「训练质量分」**：先不做。等逐组的心率 / 休息数据攒够以后，在负责人自己的数据和合成数据上试，再决定（Q4）。

**不做**：动作示范图 / 视频、动作库搜索、新增计划外的动作（可以用语音让 Jarvis 加，第 2 期）、超级组的专门界面（第 1 期按顺序逐个记）、肌肉图。

### 2.2 饮食快速记录（P0 的后半，第 2 期）

**触发**：表盘小组件「记一餐」；app 首屏按住 Jarvis 键；Siri「用 Watch2Whoop 记一餐」（App Intents，第 3 期）。

**两条路，各自最少步数**：

| 路 | 步数 | 依赖 |
|---|---|---|
| 语音：按住说「午饭一碗牛肉面加一个蛋」→ 松开 | 1 次按住 | 用户的 AI 在 app 内可用（自己的 API key 或托底 AI）；要联网 |
| 快记：点模板「常吃的早餐」 | 2 次点按（打开 → 点模板） | 不依赖 AI；可离线排队（现有接口 `POST /meal-templates/{id}/log`，按 `client_id` 幂等） |
| 喝水：点一下 | 2 次点按 | 现有接口 `POST /water` |

**屏幕**：

```
 说话中                      记好了                      快记
┌───────────────┐          ┌───────────────┐          ┌───────────────┐
│               │          │ 午餐          │          │ ┌─────┐┌─────┐│
│  ▁▃▅▇▅▃▁▃▅▃   │          │   520 kcal    │          │ │早餐A││午餐B││
│               │          │ 蛋白 32 g     │          │ └─────┘└─────┘│
│ 午饭一碗牛肉  │          │ ━━━━━━─── 今天│          │ ┌─────┐┌─────┐│
│ 面加一个蛋    │          │ ┌───────────┐ │          │ │加餐C││ 水  ││
│               │          │ │   撤销    │ │          │ └─────┘└─────┘│
└───────────────┘          └───────────────┘          └───────────────┘
```

- **说话中**：音量条 + 识别出的文字（服务器转写时，文字在松手后才出现；见第 4.3 节）。往上滑取消。
- **记好了**：餐次、热量、蛋白质、今天热量的进度条。记录直接执行；「撤销」要确认（一个两键的确认屏）。
- **快记**：最多 4 格（3 个最常用的模板 + 喝水），不滚动。模板在手机上建和排序。

**各输入方式**：语音 = 内容；点按 = 模板 / 撤销；表冠 = 不用；触感 = 记好了成功震动、失败（没联网、没听清）错误震动。

**不做**：拍照、改克数、看营养素明细、建模板、食谱。记错了说「刚才那餐改成半碗」，或回手机改。

### 2.3 语音问 Jarvis（P1，第 2 期）

和 2.2 是**同一个键、同一条通道**：按住说话 → 文字 → `POST /v1/assistant/chat`。说的是记录，Jarvis 就调写工具；说的是问题，就回答。手表不区分「记」和「问」两个入口。

**最少步数**：1 次按住。

**屏幕**：回答 = 一张卡（一个图形 + 一个数，沿用手机 Jarvis 卡片的类型）+ 最多两行字 + 「AI 生成」标记。超过两行时，末尾一个「在手机上继续」（把这轮对话的 `conversation_id` 交给手机）。

```
┌───────────────┐
│ 还能吃        │
│   680 kcal    │
│ ━━━━━━━──     │
│ 蛋白还差 40 g │
│ AI 生成       │
└───────────────┘
```

**约束（重要）**：

- 只有用户选的 AI 是「自己的 API key」或「托底 AI」时，手表上才有语音键。用订阅类客户端（MCP）或管家链接的用户，AI 在别的 app 里，手表上没法调，语音键不显示，只留快记。
- 托底 AI 的同意、额度（现有规则）不变；第一次同意只能在手机上做。
- 回答要短：请求里带 `page: "watch"`（字段已有），服务器的角色设定按这个值要求「先给数，最多两句」（需新增：设定里加一段，手表和手机共用同一套工具）。
- 语音转写的每日条数上限（现有）和手机共用。
- 语音直接发送还是先确认：手机上由开关 `jarvis_voice_direct` 控制（同意书的约定）。手表上没有输入框可以改字，推荐「松手后文字停留 1.5 秒，可以点取消，不点就发」，仅在该开关打开时提供语音键（Q6）。

**不做**：对话历史、多轮追问界面（可以连续按住再说一句，上下文靠 `conversation_id`）、切换 AI、图片、体态分析、朗读回答（第 3 期再评估）。

### 2.4 今天一眼（P1，第 2 期）

**触发**：打开 app 且没有进行中的训练时的首屏；点表盘小组件。

**最少步数**：0（抬腕看小组件）或 1（点开）。

**屏幕**：手机「今天」的那个仪器的缩小版：一个恢复刻度盘（数字 + 弧 + 最多 4 个字的判断词），下面两个读数（睡眠、负荷）。往下是两个键：「开始训练」（今天有计划时）和 Jarvis 键。没有别的。

```
┌───────────────┐
│    ╭─────╮    │
│    │ 82% │    │
│    ╰─────╯    │
│   可上强度    │
│ 睡眠 88 负荷 2.8│
│ [开始训练] (J)│
└───────────────┘
```

**数据**：手机算好的今天的分数（本地优先：分数在手机上算），由手机推给手表；手表不算分。数据旧了（手机很久没同步）显示时效标记，和手机的同步胶囊同一套状态。点刻度盘**不**展开第二层（原因在手机上看）。

**表冠**：不用。**语音**：按住 Jarvis 键。**触感**：无。

### 2.5 表盘小组件和 Smart Stack（P1，第 3 期）

| 形态 | 内容 | 点了去哪 |
|---|---|---|
| 圆形（表盘角 / 圆位） | 恢复弧 + 数字 | 今天一眼 |
| 矩形（Smart Stack / 大位） | 恢复、睡眠、负荷三个数 + 小弧；训练进行中时变成「卧推 2/4 · 休息 1:12」 | 今天一眼 / 当前训练 |
| 角落 / 行内 | 负荷数字 + 弧；或一行「恢复 82% · 负荷 2.8」 | 今天一眼 |
| 快捷键（圆形，无数据） | 「开始训练」「记一餐」 | 直接进对应场景 |
| 控制中心 / 操作按钮的控件（watchOS 26 起） | 「开始训练」「按住说话」 | 同上（第 3 期，待验证 V7） |

- 小组件只放「数 + 弧」，颜色规则和手机一致（恢复用状态色，睡眠 / 负荷用类别色）。
- **刷新**：恢复和睡眠一天变一次（早上），负荷白天会变。手机算出新分数后推给手表、手表重载小组件；系统对刷新次数有预算（待验证 V6：一天实际能刷几次）。
- **Smart Stack 的时机**：早上醒来后（恢复出来了）、计划的训练时间前后（开始训练）、训练进行中（系统会自动把有训练会话的 app 顶上来）。
- 不做：圈子、饮食进度、趋势的小组件（先看前三种有没有人用）。

### 2.6 明确不做的场景

| 不做 | 原因 |
|---|---|
| 趋势、报告、睡眠阶段图、身体年龄、化验 | 要读图和比较 |
| 圈子的任何页面 | 浏览型；提醒走系统通知 |
| 训练计划编辑、动作库、动作示范 | 训练前的准备，在手机上做 |
| 拍照记餐、食谱、采购 | 没有相机；编辑型 |
| 登录、注册、同意书、AI 设置、同步中心 | 设置一律在手机 |
| 长对话、对话历史、切换 AI | 手表只做一问一答 |
| 独立记录跑步 / 骑行路线（GPS、配速、分段） | 系统的「体能训练」app 已经做得很好，记下来的训练本来就会同步进来。我们只接力量训练，有氧 / 球类最多做「开始 / 结束」（Q3） |
| 睡眠追踪、心电图、血氧的采集界面 | 用系统自带的，数据经 HealthKit 进来 |
| 文字键盘输入 | 一切文字靠语音 |
| 通知里的长文字、每日总结朗读 | 文字趋近于零 |

## 3. 取舍原则

手表屏幕大约是手机的六分之一，抬腕一次只有几秒。判断一个东西要不要上手表，按顺序问四个问题，任何一个答「否」就不上：

1. **是不是当下要做的事**（正在练、正在吃、刚抬腕）？回顾和规划都不是。
2. **手机这时是不是不方便**（在柜子里、手上有东西、在做饭）？手机顺手的事不搬到手表。
3. **能不能一次交互做完**（一次点按，或一句话）？做不到就砍到能做到为止。
4. **是不是只有手表有这个数据或时机**（实时心率、触感提醒、表盘）？是的话优先级提高一档。

**硬性上限**（每一屏都要满足）：

| 项 | 上限 | 手机 2.0.1 的对应规则 |
|---|---|---|
| 主体 | 每屏 1 个 | 每个 tab 一个仪器 |
| 一次交互 | 记一组 ≤ 2 秒；记一餐 ≤ 8 秒（含说话）；看一眼 ≤ 3 秒 | 手机没有时间上限，手表新增 |
| 数字 | 每屏 ≤ 4 个，其中只有 1 个是大数 | 手机首屏 ≤ 6 个、1 个大数 |
| 文字 | 每屏 ≤ 6 段短标签，**0 个句子**；标签 ≤ 4 个汉字或 2 个英文词 | 手机 ≤ 15 段、0 个句子、标签 ≤ 6 个汉字 |
| 主按钮 | 每屏 1 个，占满宽度，高度不小于屏幕的四分之一 | 手机点按区 ≥ 44 pt |
| 层级 | 最多 2 层（场景屏 → 一个确认 / 调整屏）；没有 L1 / L2 / L3 展开 | 手机 L0–L3 渐进展开；手表只有 L0，更深的层「在手机上看」 |
| 横滑 | 每屏 1 个含义 | 相同 |
| 颜色 | 每屏 ≤ 2 种色相（一种状态色或类别色 + 墨色） | 手机 ≤ 3 种 |
| 滚动 | 场景屏不滚动；只有快记和结束屏允许一屏以内 | 手机允许折叠线以下 |

**直接沿用手机 2.0.1 的规则**：颜色的含义（good / mid / bad 只表示状态，sleep / train 只表示类别）、刻度盘和弧的画法（细轨道、刻度就是标尺）、数字带单位、变化带符号且都表示「和你平常比」、分数旁的「非诊断」和 AI 回答的「AI 生成」（手表上是一个小标记，句子在手机上）、只用 Lucide 图标、不用渐变 / 发光 / 饼图、双语（`tr("中文", "English")`）。

**和手机不同的地方**：没有底栏和 tab（手表 app 是「一个首屏 + 当前场景」）；背景永远是黑（省电，也是 watchOS 的惯例）；字号按手表的尺寸另定一套（需要设计）；常亮显示（手腕放下）时只留倒计时和组数，心率每几秒更新一次，不放动画。

**精简和功能的取舍，为什么这样定**：手表上每多一个入口，核心的那一下点按就多一步或多一次误触。所以宁可让 80% 的情况一下完成、剩下 20% 回手机，也不在手表上做「完整但要翻找」的功能。验证标准很简单：**训练中不解锁手机能不能把整次训练记完**。能，手表端就成立；别的都是加分项。

## 4. 技术可行性和约束

状态说明：**已核对** = 查过 Apple 文档或可靠资料；**待验证** = 资料不足或说法不一，要在真机上试（第 4.10 节）。

### 4.1 工程形态

- 在 `apps/ios/project.yml`（XcodeGen）里加两个 target：watchOS app（纯 SwiftUI）和它的小组件扩展（WidgetKit）。跟着 iPhone app 一起打包发 TestFlight，用户装了手机 app 后手表上自动出现（或在 Watch app 里手动装）。
- 手表和手机共用的代码（模型、颜色 token、`tr()`、训练计划的数据结构）抽成一个本地 Swift 包，两边都依赖。手表**不**带 GRDB、不带算法包。
- Bundle ID 是 iPhone app 的 ID 加后缀；需要在开发者账号里给手表 app 开 HealthKit 能力（负责人 / 发版的人操作，Q9）。
- 不跑 iOS 构建的约束下，这部分没有实测；第 1 期的第一步就是「空壳 target 能编过、能装到真表」。

### 4.2 训练会话和实时心率

- **API**：`HKWorkoutSession` + `HKLiveWorkoutBuilder`（watchOS 5 起）。活动类型用传统力量训练。会话进行中，app 在手腕放下后继续运行、心率传感器保持高频采样，训练结束时系统把一条训练（含心率、活动能量）写进 HealthKit。**已核对**（常规用法）。
- **这条训练怎么进我们的系统**：不用新通道。它进手机的 HealthKit → 现有同步引擎 → 服务器的 `workouts` 表 → 现有的 TRIMP / 分区 / 训练后心率恢复 / 负荷计算。力量记录和这条训练按天合并也是现有逻辑。
- **手表上的 HealthKit 授权**是独立的一次（读心率、写训练）。授权弹窗只能用户自己点。
- **和系统「体能训练」app 的冲突**：同一时间只能有一个训练会话。用户已经用系统 app 开了力量训练再打开我们的，后开的会顶掉先开的。**待验证 V2**。对策：检测到已有会话时，我们不开自己的会话，只记组（没有实时心率，其余不变）；这也是「轻量模式」，可以作为一个设置。
- **镜像到手机**（`startMirroringToCompanionDevice`，watchOS 10 / iOS 17 起）：手表的会话可以在手机上实时出现，双方还能互发数据。好处是手机上的训练页可以跟着手表一组一组地亮。但开发者论坛上有新系统上镜像偶尔建立不起来的报告。**结论**：不把它当主通道，第 3 期再作为「手机实时跟随」的增强。
- **电量**：训练会话期间的耗电和系统「体能训练」app 同一量级（心率传感器 + 屏幕）。我们自己能控制的是：常亮状态下降低刷新、不做持续动画、不在训练中联网（事件攒着发）。**待验证 V3**：一小时力量训练实际掉电多少。

### 4.3 语音输入

| 方式 | 可行性 | 优点 | 缺点 |
|---|---|---|---|
| A. 手表本机识别（`SFSpeechRecognizer` / iOS 26 的 `SpeechAnalyzer`） | **不可行**：Apple 文档里这两个框架的支持平台都没有 watchOS（已核对文档列表；watchOS 27 的 SDK 是否有变化，待验证 V4） | — | — |
| B. 手表录音 → 服务器转写（现有 `POST /v1/assistant/transcribe?fix=1`，16 kHz 单声道 WAV） | 可行（手表有 `AVAudioEngine` / `AVAudioRecorder`）。**推荐为主** | 和手机同一个识别服务、同一套用户词纠正；录音不落盘、不出服务器（现有规则） | 要联网；文字在松手后才出现（没有边说边出字）；10 秒录音约 320 KB，经手机蓝牙上传的耗时待验证 V4 |
| C. 系统听写（文本框唤起的系统输入界面） | 可行。**推荐为兜底** | 不用自己处理音频；有的语言可离线 | 界面是系统的，要多点一下；拿不到录音，不能用我们的词纠正 |
| D. 录音文件传给手机，手机用本机识别 | 可行但慢 | 不经服务器 | 手机必须在旁边且能被唤醒；延迟最大 |
| E. Siri + App Intents（「用 Watch2Whoop 记一餐」） | 可行，作为**额外入口**（第 3 期） | 不用打开 app | 中文参数识别的准确度不可控；不能替代 app 内语音 |

推荐：**B 为主，C 兜底，E 作为入口**。B 的体验目标：松手到出字 ≤ 2 秒（Wi-Fi / 蜂窝）或 ≤ 4 秒（经手机蓝牙）；达不到就把默认换成 C。

### 4.4 联网：独立还是经手机

三种通道，各有用处：

| 通道 | 用在哪 | 说明 |
|---|---|---|
| WatchConnectivity（手表 ↔ 手机） | 训练事件、今天的分数、训练计划快照、快记模板、登录 | `transferUserInfo`：排队、保证送达、对方没开也行，适合「记了一组」；`updateApplicationContext`：只留最新一份，适合分数和计划；`sendMessage`：双方都在线时的即时消息 |
| 手表自己发 HTTPS（`URLSession`） | 语音转写、Jarvis 对话 | 手机在旁边时系统自动经手机走；手机不在时走手表的 Wi-Fi / 蜂窝。**已核对**（watchOS 的常规行为） |
| 训练会话镜像 | 手机实时跟随（第 3 期） | 见 4.2 |

**推荐的分工**：**记录类数据一律经手机**（手机是本地库和离线队列的唯一写入方，见 4.6）；**AI 类请求由手表直接发**（把 SSE 流经 WatchConnectivity 转一道既慢又脆）。

Jarvis 的回答是 SSE 流。手表上经手机代理时长连接是否稳定，**待验证 V4**。备选：给对话接口加一个不流式的短回答模式（需新增），手表只要最后的卡片和两行字，本来也不需要逐字出现。

### 4.5 登录 / 鉴权

- 手表**没有登录界面**。手机登录后把凭据带过去。
- 钥匙串不能在手机和手表之间直接共享访问组（已核对；iCloud 钥匙串同步是另一回事，本项目的凭据是「仅本机」，不走它）。
- **推荐做法**：手表拿**自己的设备 token**，不复制手机的。流程：手机用现有的 `POST /v1/account/web-login-code` 申请一个一次性登录码（10 分钟有效，权限不超过手机自己的）→ 经 WatchConnectivity 发给手表 → 手表用现有的 `POST /v1/web/login-code {code, client: "app"}` 换成自己的 token，存进手表的钥匙串。好处：手表的 token 可以单独吊销；手机退出登录时通知手表删掉。
  - 需要的小改动（需新增）：登录码的用途标签现在是给内嵌网页用的，要允许标成「手表」并在「已连接的设备」里显示出来；手机退出登录时连带吊销手表的 token。
- 第 1 期（只有训练记组）**手表完全不需要 token**：所有数据都经手机。token 从第 2 期（语音）才需要。
- 服务器地址（自托管，每个部署不同）同样由手机带过去。

### 4.6 本地优先里手表的位置；离线排队

本项目的方向是「计算在手机上，服务器留一份同步副本给 AI 和圈子」。手表在这里是**手机的外设**，不是第三个数据节点：

```
手表（采集 + 输入）            手机（唯一的本地库 + 算分）        服务器（副本，AI / 圈子）
  训练会话 ──► HealthKit ─────► 同步引擎 ───────────────────────► ingest
  记一组事件 ─► 事件队列 ─WC──► 并进当天训练草稿 ─► 离线队列 ───► PUT /training/session/{day}
  快记 / 喝水 ► 事件队列 ─WC──► 离线队列 ───────────────────────► 现有接口（client_id 幂等）
  今天的分数 ◄─WC（最新一份）── 本机算分
  语音 ───────────────────────────────────────────────────────► /transcribe、/chat（直连）
```

- **手表上存什么**：今天的训练计划快照、没交出去的事件、最近一份分数、最多 4 个快记模板、自己的 token 和服务器地址。不存历史。
- **为什么训练记录不由手表直接写服务器**：当天训练在服务器上是「整份覆盖 + 版本号」，两台设备各写各的会互相覆盖或冲突（409）。让手机做唯一写入方，手表只发「第 N 个动作第 M 组：重量、次数、完成时间、这组的心率」这样的**事件**，每个事件带唯一 id，手机按 id 去重后并进草稿。手机上同时也在改时，以事件的时间顺序合并，同一组后到的覆盖先到的。
- **手机不在身边（放在柜子里、没带）**：事件留在手表的队列里，`transferUserInfo` 会在两台设备重新连上后自动送达；训练会话照常进行，训练结束时那条训练照常进 HealthKit。也就是说**整次训练可以完全离线记完**。训练计划快照是手机上次打开时推过来的；当天没同步过计划时，手表显示「在手机上打开一次」（不让用户在手表上凭空建计划）。
- **手机长期不在（只带手表出门，蜂窝款）**：记录会一直等到回到手机旁边。要让手表自己把逐组记录交给服务器，需要一个「只追加」的逐组接口（需新增），**不建议在前三期做**：这种用法少，而且会引入第二个写入方。
- **提交训练**（把打了勾的组写成一条力量记录）：由手机在收到「训练结束」事件后执行现有的提交。手机当时不在线则进它自己的离线队列，和现在一样。

### 4.7 后台和电量

- 训练会话期间：app 持续运行（4.2）。
- 非训练时：手表 app 基本不在后台做事。分数靠手机推（WatchConnectivity 会在后台唤醒手表 app 一小段时间来接收），小组件靠时间线 + 推送后重载。不做定时轮询。
- 语音：只在前台；录音时长上限 30 秒。
- 常亮显示：做组中只显示组数和重量，休息中只显示倒计时；不显示心率的逐秒变化。

### 4.9 最低系统版本

| 选项 | 能用到什么 | 代价 |
|---|---|---|
| watchOS 10 | 新版 SwiftUI 导航和排版、Smart Stack 小组件、训练会话镜像 | Double Tap 不能给自己的按钮用 |
| **watchOS 11（推荐）** | 以上 + 把 Double Tap 指定给主按钮、Smart Stack 的相关性提示、手机的实时活动自动出现在 Smart Stack | 放弃只能升到 watchOS 10 的旧表（Series 4 / 5、第一代 SE） |
| watchOS 26 | 以上 + 控制中心 / 操作按钮的控件、新的相关性框架 | 再放弃一批表；这些能力可以用 `if #available` 单独开，不必抬高最低版本 |

推荐 **watchOS 11**：Double Tap 是「不碰屏幕记一组」的关键，值得为它定版本；更新的能力按可用性判断分别启用。配对的 iPhone 这时至少是 iOS 18，高于 iPhone app 的最低 iOS 16，不冲突（只是 iOS 16 / 17 的用户用不上手表端）。Double Tap 本身需要 Series 9 / Ultra 2 及以后的表，更早的表退回点按。负责人自己的表和系统都在这个范围内。

| V2 | 系统「体能训练」app 已有会话时，我们再开会话会怎样 | 真表上先开系统的力量训练，再开我们的 | 检测到已有会话就走轻量模式（只记组） |
| V3 | 一小时力量训练的掉电 | 真表满电练一次，对比系统 app 的一次 | 降低心率显示频率；常亮时停更新 |
| V4 | 语音：录 10 秒 → 上传 → 出字的耗时（Wi-Fi、经手机蓝牙、蜂窝三种）；SSE 在手表上是否稳定；watchOS 27 SDK 里有没有新的本机识别（第 2 期开始前） | 真表计时各 10 次；查 SDK 头文件 | 默认改成系统听写；对话用不流式模式 |
| V5 | Double Tap 在做组中（握着器械、手腕弯着）的识别率，会不会误触 | 负责人实际练两次，数成功 / 失败 / 误触 | 默认关，作为可选项 |
| V6 | 小组件一天实际能刷新几次；手机推送后多久更新（第 3 期开始前） | 真表记录一天 | 小组件只显示恢复（一天一变），负荷只在 app 内看 |
| V7 | 控件（控制中心 / 操作按钮）能不能直接开始录音（第 3 期开始前） | 真表试 | 控件只负责打开 app 到对应场景 |
| V8 | 手机在柜子里一小时后，事件队列回连时是否全部按序送达 | 开飞行模式的手机 + 手表记 20 组，再连上 | 手表侧加「未送达 N 条」标记和手动重发 |

## 5. 分期

### 第 1 期：训练记组 demo

**范围**（只有这些）：

- 手表 app 空壳 + 和手机的 WatchConnectivity 通道；手机把今天的训练计划快照推给手表。
- 「开始训练」→ 训练会话（实时心率）→ 做组中 / 组间休息 / 训练结束三个状态（2.1）。
- 记一组：点按；Double Tap（可选项，默认开，按 V5 的结果调整）；表冠调次数 / 重量。
- 休息倒计时 + 到点震动；休息屏的心率和回落值。
- 事件经手机并进当天训练，手机上的训练页看到同样的组；训练结束后手机执行提交。
- 手机不在身边时离线记完、之后补交。

**不含**：语音、饮食、今天一眼、小组件、RIR、「可以开始下一组」的心率提示、逐组心率上传到服务器（先只存在手机本地）、后端改动（**第 1 期后端零改动**）。

**为什么选它**：它是负责人点名的场景里唯一「只有手表能做好」的；不依赖 AI、不依赖联网、不动后端，范围最小；负责人每周练五次，一周内就能知道值不值得继续。

**验收标准**：

1. 一次真实的力量训练（≥ 15 组），全程不解锁手机，全部在手表上记完。
2. 每组从「放下器械」到「记好」≤ 2 秒，1 次点按或 1 次 Double Tap。
3. 训练结束后 1 分钟内（手机在旁边时），手机的训练页显示的组数、重量、次数和手表上记的完全一致；提交后服务器上是一条力量记录，没有重复。
4. 手机开飞行模式练完，恢复连接后数据完整到达，顺序正确（V8）。
5. 这次训练在 HealthKit 里是一条力量训练，手机同步后「今天」的负荷照常算出。
6. V1–V3、V5、V8 有书面结果。
7. 界面满足第 3 节的上限；双语；数字全部来自真实计划，没有写死的示例数据。

### 第 2 期：语音（记一餐、问 Jarvis）+ 今天一眼

- 手表设备 token（4.5）；按住说话 → 服务器转写 → Jarvis（2.2、2.3）；回答卡；撤销的确认屏。
- 快记 4 格（模板 + 喝水）。
- 首屏变成「今天一眼」（2.4），分数由手机推送。
- 后端：登录码用途标签和连带吊销；`page: "watch"` 的短回答设定。
- 训练中按住说话改这一组 / 换动作。

**验收**：说一句「午饭……」到看到「记好了」≤ 8 秒（Wi-Fi）；记录出现在手机的饮食页且只有一条；10 句常见的饮食 / 提问里至少 9 句结果正确（负责人自己测）；没联网时语音键变灰、快记仍可用并在联网后送达；用订阅类 AI 的测试账号上语音键不出现；手机退出登录后手表 1 分钟内失效；V4 有书面结果。

### 第 3 期：表盘小组件、Smart Stack、Siri

- 圆形 / 矩形 / 角落 / 行内小组件 + 两个快捷键小组件（2.5）；训练进行中的矩形小组件。
- Smart Stack 的相关性（早上、训练时间）。
- App Intents：「开始训练」「记一餐」；watchOS 26 起的控件。
- 可选：训练会话镜像到手机（手机实时跟随）。

**验收**：早上恢复分算出后 15 分钟内小组件更新；从表盘到「做组中」≤ 2 次点按；Siri 短语能开始训练；一周内小组件没有出现过「过期一天以上」的数据；V6、V7 有书面结果。

### 第 4 期：训练质量的数据和回看

- 后端：逐组记录加心率 / 休息 / 完成时间字段（4.8）；手机把第 1 期起存在本地的逐组心率补传。
- 手机上的训练详情加「每组心率峰值 → 组间回落」的图；每个动作最后一组的 RIR（如果 Q5 选了要）。
- 「可以开始下一组」的心率提示（规则 + 参数 + 出处）。
- 在负责人自己的数据和合成数据上评估要不要做「训练质量分」（Q4）。

**验收**：手机上任意一次手表记的训练都能看到逐组心率图；心率提示可在设置里关；评估结论写进文档再决定下一步。

### 之后再评估（不排期）

日记 / 补剂在通知上直接打卡；有氧 / 球类的「开始 / 结束」；回答朗读；蜂窝款手表完全脱离手机的逐组上传；超级组界面。

## English summary

A plan for a watchOS companion to the native iPhone app; no code yet.

- **Role**: the watch is the capture key on the wrist (log a set, say a meal, ask one question, glance at today's recovery and strain); the phone stays the dashboard. No trends, history, plan editing, circles pages, settings or sign-in on the watch.
- **Scenarios by priority**: (1) logging sets during strength training: one tap or one Double Tap per set, automatic rest timer with live heart rate and a haptic at the end; (2) meals by voice or by one of four quick templates; (3) one question to Jarvis, answered with one card and at most two lines; (4) today at a glance; (5) complications and Smart Stack.
- **Training quality** is shown as facts (sets done, change against the last session, heart-rate drop during rest, rest time), not as a score.
- **Trade-off rule**: one subject per screen, one interaction per task (log a set ≤ 2 s), ≤ 4 numbers, zero sentences, two levels at most; anything deeper says "continue on the phone". Colours, dial grammar, tags, Lucide icons and the bilingual rule follow the phone's 2.0.1 direction.
- **Architecture**: the watch is a peripheral of the phone in the local-first design. Records travel as events over WatchConnectivity to the phone, the single writer of the local database and the offline queue; the workout itself reaches the server through HealthKit and the existing sync engine. Only AI requests (transcription, chat) go from the watch straight to the server, with the watch's own device token minted through the existing one-time login code.
- **Voice**: no on-device speech framework is listed for watchOS, so the watch records audio and uses the existing server transcription; system dictation is the fallback.
- **Phases**: 1) set-logging demo (no backend change); 2) voice + today glance; 3) complications, Smart Stack, Siri; 4) per-set heart-rate data and its charts on the phone.
- Items marked 需新增 do not exist in the backend yet; items marked 待验证 need a check on a real watch (section 4.10). Nine owner decisions are listed in section 6.
