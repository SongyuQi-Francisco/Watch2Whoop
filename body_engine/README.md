# Body Engine

The in-house part of the body management system: daily metrics, sleep, scores, journal, supplements, lab results, events, rule reminders, AI assistant. Multi-user (every table has a `user_id`, each person has their own tokens, and viewing someone else's data needs a `shares` grant). For the design see sections 6, 7, 12 and 13 of `../docs/system-design.md`.

## Running
```bash
# From the repository root: start the database and the API (http://127.0.0.1:8100, docs at /docs)
docker compose up -d --build

# In body_engine/: command line (connects to 127.0.0.1:5433, password read from ../secrets/body_db_password)
uv run body-engine migrate
uv run body-engine user-add --name NAME [--role owner] [--birth-date 2001-06-15] [--height-cm 178]
uv run body-engine token-create --user-id 1 --name PURPOSE   # the plaintext is shown only this once
uv run body-engine import-apple-export --user-id 1      # run health_sync/parse_export.py first
uv run body-engine import-shortcut --user-id 1          # archive/health_*.txt uploaded by the iOS Shortcut (new files only; --all re-imports everything) → shortcut_samples etc., format in ../docs/shortcut-sync-spec.md
                                                        # --rebuild-since 2026-10-01: recompute the Shortcut's days from shortcut_samples and re-choose every daily metric since then
                                                        # (each source's daily value is kept in daily_metric_sources; cumulative = largest complete source, spec §5)
uv run body-engine ow-link --user-id 1                  # create the matching user in Open Wearables (just shows it if it already exists)
uv run body-engine import-ow --user-id 1                # incrementally pull daily metrics, sleep and workouts from OW; --full recomputes everything, --start/--end pick the dates
uv run body-engine import-workouts --user-id 1          # pull only OW's workouts → workouts (all history by default; for backfill / recompute after changing training/params.py)
uv run body-engine compute-scores --user-id 1           # sleep / recovery / strain / muscular load → daily_scores (recomputes everything from the scoring start date, about 20 s; --start/--end only limit which days are written)
                                                        # afterwards it also computes body age (weekly, healthspan_weekly) and stress for the last 90 days (stress_daily), about 30 s in total
uv run body-engine sparky-link --user-id 1 --key-name owner  # connect SparkyFitness: validates secrets/sparkyfitness_api_key_owner_ro (must be a read-only key)
uv run body-engine import-records --user-id 1           # backfill supplements, lab results, events, exercises and journal from body-management.md, then print a check table
uv run body-engine journal-init --user-id 2             # create the default journal items for a family member (existing ones are left alone)
uv run body-engine link-exercises --user-id 1           # write SparkyFitness exercise IDs into exercise_meta.app_exercise_id (--dry-run only shows the mapping table)
uv run body-engine evaluate-rules --user-id 1           # rule reminders → reminders (today by default, --date to choose; runs after compute-scores every day)
uv run body-engine set-sleep-goal --user-id 1 --bedtime 00:00   # bedtime target (moves earlier step by step starting from the last 7 nights' average; --wake / --pace / --step-days optional)
uv run body-engine memory-init --user-id 1 --from-md    # the body butler's initial profile card + status card + the "fixed breakfast" template (transcribed from the database + body-management.md; only fills what is missing)
uv run body-engine recipes-init --user-id 1             # recipe metadata: fill in the 25 dishes migrated into SparkyFitness according to body-management.md (existing ones are left alone)
uv run body-engine refresh-status --user-id 1           # recompute the automatically computed items of the status card (the hourly job runs it; the Today page also refreshes it on read when older than 30 minutes)
uv run pytest                                           # each database test uses its own body_test_* database (rebuilt every time); skipped if it cannot connect
```
All imports are idempotent and can be re-run. Source priority is `ow` > `apple_export` > `shortcut`.
For OW's deployment and API key see `../deploy/open-wearables/README.md` (the key is read from `../secrets/open_wearables_api_key`, the address is `BODY_OW_URL`, default http://127.0.0.1:8200).
The OW importer's rules (cumulative metrics de-duplicated by time window + source priority, the export day itself not written, the XML unit problem) are written at the top of `src/body_engine/importers/ow.py` and in section 10 of the system design.
SparkyFitness (workouts, meals, weight) is not imported; it is read live through its API when needed (`src/body_engine/sparky_client.py`, one read-only key per person; only the body butler's write tools use the read-write key; address `BODY_SPARKY_URL`, default http://127.0.0.1:8300; key directory `BODY_SECRETS_DIR`, default `../secrets`). Why a read-only database role is not used is explained at the top of that file. For deployment see `../deploy/sparkyfitness/README.md`.

## Scores (`src/body_engine/scores/`)
WHOOP-style sleep score, sleep need / sleep debt / sleep performance, recovery score (HRV currently uses SDNN), strain (Edwards TRIMP), CTL / ATL / TSB. For the formulas, parameter values, differences from the design and backfill results see "Implementation notes" in section 7 of the system design.
- `params.py`: all parameters and `ALGO_VERSION` (when you change a parameter that affects results, bump the version, then run `compute-scores`).
- `sleep.py` / `recovery.py` / `strain.py`: pure functions; `inputs.py`: reads `sleep_sessions`, OW raw samples and iOS Shortcut samples (`shortcut_samples`, including ungrouped raw heart rate; falls back to the archive when the table is empty); `engine.py`: day-by-day computation and database writes; `store.py`: reads scores (shared by the API and the assistant).
- One row per day; a score that cannot be computed is left empty, with the reason in `flags` (`{code: explanation}`), and the sub-scores and baselines in `details`.
- Needs OW to be running (to pull raw heart rate etc.); the iOS Shortcut archive is read from `$BODY_HEALTH_DATA_DIR/archive` by default.
- `muscle.py`: muscular load `muscle_load` = Σ reps × weight (kg, a relative quantity) of the working strength sets in SparkyFitness workout logs, details in `details.muscle`; not computed for users who have not connected SparkyFitness (v1.1).

## WHOOP-comparable analysis (`src/body_engine/insights/`)
Body age / pace of ageing, stress, today's strain target, sleep coach, health monitor, sleep details (regularity SRI, efficiency, latency), heart rate zones, VO₂max level, weekly / monthly reports. Item-by-item mapping in `../docs/whoop-feature-map.md`; the algorithms, literature, anchor points, API fields and real-data results are in "Body age and other analyses" in section 7 of the system design.
- `healthspan_params.py`: all curve parameters of body age and their sources (bump `ALGO_VERSION` when you change them); `healthspan.py` pure functions; `healthspan_store.py` reads data, takes weekly snapshots, writes / reads `healthspan_weekly`.
- `stress.py` (writes `stress_daily`), `coach.py` (strain target, sleep coach, health monitor, computed on demand), `sleep_detail.py`, `fitness.py`, `reports.py`; `views.py` holds the read functions shared by the API and the butler tools, `api.py` the routes, `tools.py` the butler tools, `jobs.py` the parts compute-scores runs along the way (a failure in one does not affect the scores).
- The sleep coach uses the bedtime target of the rules session (`goals/`): if that module is present it recommends according to the target, otherwise only according to sleep need.
- Tests: `tests/test_insights.py` (formula edge cases, insufficient data, time zones), `tests/test_insights_db.py` (test database body_test_insights, created if missing, emptied every run).

Rules for health records: reading someone else's needs the matching scope in `shares`; **writes (POST / PUT / PATCH / DELETE) can only be made for yourself** (use `me` or your own ID in the path), and the token needs `write`.
Without an `Authorization` header the Today page's cookie is used for authentication (`web/session.py`); writes using the cookie must also send `X-Body-Web: 1` (CSRF protection).

## Today page (`src/body_engine/web/`)
A mobile-first PWA served by Body Engine itself (`/app/`, `/` redirects there), with no build step: `static/` holds plain JS + CSS, charts are hand-written SVG, no external libraries (works offline too). v2 (2026-10-17) was redone in a "minimal, premium" style: few words, the numbers speak, and explanations and details are tucked into bottom sheets you open on tap.
- Single entry point (system design section 0): phone and computer both use only the Today page, the front end has no link to SparkyFitness, and the API no longer returns `sparky_url`; "Ask the butler" (「问管家」) is kept for now.
- 5 pages (since v2.4; there were 4 before): **Today** (a big recovery ring + one status word "fit for high intensity / train as planned / focus on recovery"; a row of 3 small metrics: sleep duration, sleep score, yesterday's strain; the training-load status tag "fresh / balanced / accumulating fatigue / fatigued", tap to see CTL / ATL / TSB; a **sleep** card (onset → wake-up, time asleep, a stage chart in the style of the Apple Watch sleep page, deep / core / REM / awake); a **bedtime target** card (tonight's target · final target, bedtimes of the last 7 nights with the stepped target as a dashed line, number of nights on target; tap to set the desired bedtime / wake-up and the pace); "Training and nutrition" (one card for the workout; nutrition progress + **quick log** meal templates: one tap logs, tap again or the toast undoes, long-press to see details and temporarily change grams; `needs_confirmation` ones show "grams to be confirmed · ask the butler"); at most 3 reminders are shown, the rest under "All") · **Trends** (Metrics: 30 / 90-day lines + 7-day mean, hold a finger to see a day; Sleep: 14 nights of stage bars, a schedule timeline, a per-night list) · **Nutrition** ("Recipes": quick log, 3 suggestions for today [with "x kcal · y g protein still to go"], search, recipe cards grouped by breakfast / lunch / dinner / snack [calories, protein, prep time, tags, health-constraint badges, favourite star; dishes you cannot make right now are dimmed]; tap to see nutrition, ingredient grams [scaled by servings], method, pick the meal and servings [0.5 steps] "log n servings", undo from the toast, favourite / can make now; "Shopping" coming soon) · **Log** (today / yesterday, "quick log" meal templates (today only), "frequent" 6–8 quick tags, "All" expands the full list by category; one tap = log "yes", tap again = undo; quantity items open to enter a number; a sheet for logging body events) · **Me** (the **body status card**: small cards grouped by group, each with label + large value + status colour tone + trend arrow (coloured by good_direction) + a mini trend line; tap to see only a one-line note and "Butler · 10/17"; the detailed profile text is the butler's underlying memory and is neither shown nor edited in the front end; observation notes are read-only + delete; supplements, body events, switch to view a family member, data update time / refresh, log out, version).
- A missing score shows "—" and an ⓘ; tap to see the reason from `flags` (`views.FIELD_FLAGS` decides which flag explains which score); when there is no sleep yet today the ring shows "last 61 · 10/16" underneath.
- Visual design: system font (SF Pro), tabular digits, weight layering; neutral greys + one low-saturation colour per state (recovery green / yellow / red, sleep one hue in different depths), cards without borders and told apart by background colour; pure black in dark mode; the only motion is the ring loading and a slight fade-in (turned off when the system "reduce motion" is on). All colours are variables at the top of `app.css`.
- **Ask the butler**: one 「问管家」 button at the bottom of each page opens `BODY_ASSISTANT_URL` (the Remote Control address of the body butler's Claude Code session, claude.ai/code/…; https only). When not configured, tapping it says "butler not connected". The AI runs entirely on a Claude subscription, and a subscription can only be used in the official client, so the Today page **has no chat box of its own and does not upload photos**: conversation and photo logging happen in the Claude app (`../docs/ai-assistant-plan.md` section 3).

## Raw watch data and cardio (`src/body_engine/rawdata/`, `cardio/`, migration 150)
Plan and evidence: `../docs/raw-data-plan.md`. Tables `heartbeat_series` (one row per Apple HRV reading: beat times + our RMSSD / SDNN), `ecg_recordings` (int16 µV waveform, zlib, Apple's classification, R peaks), `workout_hrr` (heart rate recovery after each workout).
```bash
uv run body-engine raw-slim --file export.xml --out raw.zip          # Mac: 700 MB export -> ~0.7 MB zip with only HRV beats + ECG (name / birth date removed)
uv run body-engine import-raw --user-id 1 --file raw.zip             # heartbeat_series + ecg_recordings only, idempotent (also works on the full export)
uv run body-engine hrv-compare --user-id 1 --out ../health_data/reports/hrv-compare.md   # SDNN vs RMSSD recovery, computes only (personal data: keep out of git)
```
- `rawdata/hrv.py`: RR from beat times, drops gaps / < 300 or > 2000 ms / > 25% from the series median; RMSSD needs ≥ 20 clean successive differences. Recomputed SDNN vs Apple's SDNN: r = 0.89 on the owner's 1,999 readings.

- `cardio/hrr.py`: HRR60 = peak in the last 2 min of a workout − heart rate 60 s after the end; valid only if the peak ≥ 75% HRmax. Written by `compute-scores` for the days it writes (from the raw heart rate it already loads).

## Training history (`src/body_engine/training/`)
Workouts from the watch / iOS Shortcut and SparkyFitness strength records are merged into one training history, used by the Today page's training calendar and by the body butler when planning training. For the rules, thresholds and backfill results see system design section 16.
- `importer.py`: OW's `/events/workouts` → table `workouts` (migration 080, one copy per source as is, `dup_of` marks duplicates: live sync > export.xml, OW > iOS Shortcut); pulls OW raw heart rate for the workout window to compute TRIMP and minutes in five zones (same method as the scores module), and separates active energy from the energy samples (OW's `calories_kcal` is total energy; the XML's is kJ). `import-ow` runs it every time (the hourly job), idempotent.
- `shortcut_workouts.py`: `Workout|start|end|type|duration seconds|active energy kcal|average heart rate|max heart rate|source` rows in the iOS Shortcut archive → `workouts` (source=shortcut, de-duplicated against the same workout from OW, OW wins); runs automatically during `import-shortcut`. The format is defined by `../docs/shortcut-sync-spec.md`.
- `history.py`: merges by day (SparkyFitness has no times: strength exercises attach to the longest watch strength workout of the day, cardio such as hill climbing attaches to the watch cardio workout closest in duration and uses SparkyFitness's name; unmatched ones are shown separately), intensity grades rest / light / moderate / hard / max (TRIMP → estimate from average heart rate → strength volume → duration; for strength training the higher of heart rate and volume is used), calendar and single-day detail.
- `params.py`: Chinese type names (walking is written as 「步行 / 爬坡」 "walking / hill climbing": the watch cannot tell treadmill incline, so it does not guess), de-duplication, intensity thresholds and their basis; bump `TRAINING_VERSION` after changes, then run `import-workouts`.
- `api.py` / `tools.py`: the endpoints and the assistant tools `get_training_calendar`, `get_training_day`.

## Health records (`src/body_engine/records/`)
- **Supplements**: status = active (taking) / as_needed / paused / stopped / not_needed (assessed, not needed); `rationale` why it is taken, `advice` the current advice; `journal_key` is the matching journal item (created automatically when a supplement is added).
- **Lab results**: `test_key` is an English key unified across reports (uric_acid, triglycerides, alt…), used to look at trends; `flag` = H / L / abnormal / normal. If a reference range exists the value is compared with it, otherwise the report's flag is used.
- **Events**: `time_precision` = minute / day (stored as 12:00 that day) / approx / month; `resolved_on` the date it got better.
- **Journal**: date = the day the behaviour happened; bool items 1 / 0, number items hold a value; **not recorded = missing, not "no"**. The default journal items are in `records/defaults.py`.
- **Journal analysis (first version)**: did vs did not, comparing the means of next-day recovery score, next-day resting heart rate and next-day ln HRV (SDNN); no result if either "yes" or "no" has fewer than 5 days, marked reliable only with at least 15 days each; intervals are a normal approximation and do not control for load / sleep / day of week. The outcomes are in `OUTCOMES` in `records/analysis.py`.
- **Exercises**: `exercise_ref` is an English slug (upright_row, cable_face_pull…); `app_exercise_id` is the SparkyFitness exercise ID, and `link-exercises` matches automatically by source_id / name / alias (`records/exercise_link.py`, idempotent, filled ones are not overwritten, unmatched ones are listed); to change a single one use `PUT .../exercises/{slug}` or the assistant tool `set_exercise_rule`.
- **Migration**: the data transcription for `import-records` is in `records/md_seed.py` (the 2026-10-16 version of body-management.md); every entry has an `import_key`, so re-running does not duplicate and does not overwrite later changes made in the database.

## Rule reminders (`src/body_engine/rules/`)
Double-progression weight increase / decrease (4.5), calorie adjustment by weekly average weight (5.2), pre-workout eating (4.2.1), red meat / beef short rib frequency cap (5.3.1, 5.3.2), banned / caution exercises (4.3), red recovery score / sleep debt (section 7). For the rules, thresholds, the places where something was inferred and results on real data see system design section 13.
- `params.py`: all thresholds, each with its source; the ones marked "inferred" are values taken from the most conservative reading where body-management.md is unclear. Bump `RULES_VERSION` after changing them.
- `context.py`: reads the data (SparkyFitness with the evaluated user's own read-only key; a source that cannot be read affects only the rules that depend on it); `progression.py` / `nutrition.py` / `safety.py`: the rules, pure functions `(Ctx) -> RuleResult`; `engine.py`: runs all rules and idempotently writes `reminders` (re-running does not duplicate, status is kept, ones no longer valid are deleted, old ones are kept when a rule errors) and `rule_runs`.
- Advice only; it does not change targets, plans or records in SparkyFitness.

## Bedtime target (`src/body_engine/goals/`)
Set a desired bedtime and it moves earlier step by step starting from the average bedtime of the last 7 nights (by default 20 minutes every 3 days), computing tonight's target, progress and the expected date of reaching it; the rule `sleep_goal` gives daily "go to bed before what time tonight" with a pre-bed routine, consecutive deviations, and stage achievement. Across midnight it works by "sleep day" (a night belongs to the evening before bedtime, so 06:30 is 6.5 hours later than 00:00). Details, the basis of the parameters and the API fields are in system design section 13.1.
- `params.py`: pace, tolerance, the times of the pre-bed routine and their basis (body-management.md 6.2); `sleep.py`: pure computation; `store.py`: reading/writing the table `sleep_goals` and the views; `api.py` / `tools.py`: endpoints and assistant tools.

## AI assistant (MCP)
For the remote (HTTP) MCP and multiple providers see "AI integration layer" below.
`uv run body-engine-mcp` starts a stdio MCP server whose identity is the user for `../secrets/body_engine_token_owner` (replaceable with `BODY_ENGINE_TOKEN_FILE`). The `.mcp.json` in the repository root already registers it for Claude Code. Claude Desktop has to be added by hand to `claude_desktop_config.json` (command is the absolute path of `uv`, args `--directory <repo>/body_engine run --quiet body-engine-mcp`).

Read-only tools for SparkyFitness (`assistant/sparky_tools.py`; looking up a family member's data needs the matching scope in `shares`):
| Tool | scope | Returns |
|---|---|---|
| `get_training_log` | training | Date, name and notes of each workout; for each exercise the reps, weight, RIR and duration of every set |
| `get_nutrition` | nutrition | Daily totals of calories / protein / carbs / fat and that day's target (`logged` flags days with no records), optionally each food entry |
| `get_weight` | weight | Weigh-in / waist / body fat records + weekly average weight |

Tools for rule reminders: `get_reminders` (scope reminders, today by default, with the run result of each rule), `dismiss_reminder` (write, only your own).
Bedtime target: `get_sleep_goal` (scope sleep), `set_sleep_goal` (write, only your own).
Training history tools (read-only, scope training): `get_training_calendar` (`month` or `start` / `end`, last 28 days by default: whether you trained each day, duration, intensity, active energy, strain + summary), `get_training_day` (heart rate zones, TRIMP, intensity, exercises and sets of each workout on a day).

### Tools added by the body butler (P1)
The identity and audit channel of `body-engine-mcp` can be changed with environment variables: `BODY_ENGINE_TOKEN_FILE` (the butler uses `secrets/body_engine_token_butler`) and `BODY_MCP_CHANNEL` (the butler uses `butler`). For the session itself see `../deploy/assistant/README.md` and `../assistant/CLAUDE.md`.
| Tool | Read / write (scope) | Description |
|---|---|---|
| `search_exercises` | read (training) | Find exercises in the SparkyFitness exercise library by name / alias, with the banned / caution status and key points from exercise_meta |
| `log_food` | write (nutrition) | Writes a meal to SparkyFitness (`assistant/sparky_write.py`, read-write key `secrets/sparkyfitness_api_key_<name>_rw`; before writing it confirms that the key is logged in as the account recorded by sparky-link). Checks: the date is not in the future and not older than 60 days; calories ≈ 4×protein + 4×carbs + 9×fat + 7×alcohol (a difference > max(80, 25%) is rejected); same day, same meal, same name → skipped as a duplicate (`allow_duplicates`). SparkyFitness's row-level security requires a food entry to hang off a food, so a custom food is created / reused from the content (`provider_external_id = ba:<hash>`, 1 serving = this portion); the entry carries `source=body_assistant` and a content-hash `source_id` (the server is idempotent on it) |
| `log_workout` | write (training) | Writes a workout to SparkyFitness. Exercises are matched to the library by ID → name → exercise_meta Chinese / English names / aliases → name without parentheses; **a banned exercise (exercise_meta, or 【禁用】 "banned" in the SparkyFitness description) rejects the whole workout**, checked against exercise_meta first (so it is blocked even without a SparkyFitness connection); unmatched ones get candidates; same exercise already on the same day → skipped as a duplicate (`allow_duplicate`); new exercises need `create_missing_exercises=true` |
| `log_weight` | write (weight) | Check-in: weight, body fat, waist, muscle mass, water, bone mass, BMR; range checks; a different value already on the same day is not overwritten (`overwrite`), an identical one is skipped |

| `delete_journal_entry` | write (journal) | Undo a journal item for a day (goes back to "not recorded") |
| `delete_lab_results` | write (labs) | Undo lab results the butler wrote with add_lab_results (those whose `import_key` starts with `assistant:`; migrated historical results cannot be deleted) |
| `delete_supplement` | write (supplements) | Hard-deletes a supplement entered by mistake / twice, with its own journal item (`category=supplement`, no other supplement uses the key) and that item's entries; asks first. Stopping a supplement is `update_supplement status=stopped` (keeps the history). The Today page does the same in 「我 → 补剂」 (`DELETE /v1/users/me/supplements/{id}`) |
| `add_lab_results` | write (labs) | Several tests from one lab report (`records/lab_catalog.py`): name / alias → unified `test_key` (consistent with the migrated data, so trends work), non-standard units converted (the value and the reference range together), absurd values rejected, flag computed from the reference range; same day, same test: identical skipped, different not overwritten (`overwrite`); `import_key = assistant:<date>:<key>` |
| `log_metric_snapshot` / `get_metric_snapshots` | write / read (metrics) | Scores from screenshots (Apple Readiness `apple_readiness`, sleep score `apple_sleep_score`, InBody skeletal muscle / visceral fat…) are stored in the table `metric_snapshots` (source=screenshot + source_app), **never written to daily_metrics and never overriding sensor data**; the sensor data of the same name on the same day is returned for comparison |

| `set_status_items` | write (memory) | The butler maintains status items that need judgement (current phase, injuries, goal weight goal_weight, plan adherence…); auto items cannot be written; `remove_keys` deletes outdated ones |
| `get_meal_templates` / `create_meal_template` / `update_meal_template` / `log_meal_template` / `undo_meal_log` | read / write (nutrition) | Quick meal logging (`assistant/meals.py`), same as the API above |

### Status card (`assistant/status.py`, table `assistant_status`, migration 070)
Each item: `key`, `label` (≤ 6 characters), `value` (≤ 12 characters, **without the unit**), `unit` (nullable), `tone` (good / warn / bad / neutral), `trend` (up / down / flat / null), `good_direction` (up / down / null: which direction of the trend is good), `group` (身体 body / 目标 goal / 健康 health / 训练 training / 作息 routine / 饮食 diet / 其他 other; the list is ordered by this and then by sort), `spark` (values from old → new, at most 30, may contain null; null if none), `note` (≤ 20 characters, nullable), `updated_at`, `source` (auto / assistant / seed).
| auto item | Algorithm |
|---|---|
| `weight` (体重, body weight) | Latest weigh-in (manual SparkyFitness weigh-ins first, same as the Today page); trend = mean of the last 7 days vs the previous 7 days; tone: weekly mean down 0.3–1.0kg good, down > 1.0 or up > 0.3 warn; spark = the last 30 weigh-ins |
| `to_goal` (距目标, distance to goal) | Latest weight − the `goal_weight` written by the butler; note estimates the number of weeks at the current weekly pace |
| `recovery` (恢复, recovery) | Mean recovery score of the last 7 days (≥ 67 good, 50–66 neutral, 34–49 warn, < 34 bad), trend vs the previous 7 days; spark 14 days |
| `sleep_debt` (睡眠债, sleep debt) / `sleep_hours` (睡眠时长, sleep duration) | The latest sleep debt (≤ 1h good, ≤ 2h warn); mean actual sleep over the last 7 nights (≥ 7h good, ≥ 6h warn); spark 14 days (hours) |
| `bedtime` (入睡时间, bedtime) | Mean onset time of the main sleep over the last 7 nights (≤ 00:30 good, ≤ 02:00 warn, later bad); spark = hours relative to midnight (23:30 = −0.5, 02:40 = 2.67) |
| `uric_acid` / `alt` / `triglycerides` | The latest lab result ("high 550"), more than 20% over the upper limit bad; spark = values of all past results |
| `training_week` (本周训练, training this week) | Number of days with workout records in the last 7 days (≥ 4 good, 2–3 warn); spark = the last 6 windows of 7 days |
| `red_meat_week` (红肉 7 天, red meat 7 days) | Same definition as the rule engine (journal red_meat_g first, otherwise estimated from food names; "红肉 Ng" (red meat N g) in a name is taken as labelled) |
An item that cannot be computed (no data) is deleted; if reading the data fails the last value is kept and the reason is recorded in the cursor of `sync_state` (source=status_auto).

### Quick meal logging (`assistant/meals.py`, tables `meal_templates`, `meal_logs`)
Template items: `{food, grams, kcal, protein_g, carbs_g, fat_g, sat_fat_g, purine_level (low / medium / high / null), red_meat_g, note}`, and `totals` is the sum (kcal, protein_g, carbs_g, fat_g, sat_fat_g, red_meat_g). When logging, each item becomes one SparkyFitness food entry (via `log_food`, with duplicate detection and `source=body_assistant`), with a name like 「培根 2 片（40g，红肉 40g）」 ("bacon 2 slices (40g, red meat 40g)"); the rule engine's `red_meat_estimate` and the status card count by the "红肉 Ng" annotation; when red meat is present it returns warnings (how many grams a week if eaten every day, and whether that exceeds 250g). `today_log` = the one already logged today (`{log_id, logged_at}`), so the front end can show "logged · undo".

### Recipes (`assistant/recipes.py`, table `recipe_meta`, migration 090; design in system design section 15)
Tools: `list_recipes`, `get_recipe`, `suggest_meals` (read); `create_recipe`, `update_recipe`, `log_recipe` (write, ask for confirmation).
- Nutrition is computed from ingredients (ingredients store the quantities of the whole pot; one serving = total ÷ servings); `constraint_flags` = `{purine_mg, purine_level, sat_fat_g, sat_fat_level, red_meat_g, short_rib}` (per serving; thresholds in `assistant/recipe_params.py`: purine < 150mg low, ≤ 350mg medium; saturated fat ≤ 4g low, ≤ 7g medium; one copy is stored on write and recomputed with the current thresholds on read).
- Automatic tags: high protein (≥ 30g per serving), low purine (low and no red meat), low saturated fat, quick (prep + cook ≤ 20 minutes), red meat, includes staple.
- Logging: one SparkyFitness food entry "dish name (N servings, red meat N g)", meal_logs keeps one row (recipe_id), and `last_cooked_on` is computed from entries that have not been undone.
- Suggestions: the target for this meal = the day's target (SparkyFitness, by date) − what is already logged; earlier main meals with no records are assumed eaten at the usual proportions (breakfast 25%, lunch 35%, dinner 35%), and what remains is divided proportionally between this meal and the later main meals (snacks at most 10% of the day); dishes that exceed the weekly red meat allowance or include beef short rib eaten in the last 7 days are excluded; scoring by calorie deviation, protein shortfall, purine (×1.5 when uric acid is high), saturated fat, eaten in the last 2 days, favourite, whether you can make it; a dish without staple counts as served with 90g of rice at lunch and dinner.
- When created / renamed / ingredients changed, a copy is synced to SparkyFitness (custom food `recipe:<id>` + meal); an error there does not affect Body Engine.
- Shopping preparation: ingredients carry `purchase_unit` (purchase-unit hint) and `store` (costco / woolworths / other, left empty for now).

### Grocery (`grocery/`, tables `grocery_products` / `pantry_items` / `shopping_lists` / `shopping_items`, migration 240; design in `docs/grocery-plan.md`)
Tools: `find_products`, `get_shopping_list` (read); `save_product`, `generate_shopping_list`, `add_shopping_items`, `mark_bought`, `set_pantry` (write, run directly); `remove_product`, `remove_shopping_items` (ask first, `ALWAYS_CONFIRM`).
- Product library per user: name, brand, store (free text), category, package size + unit (g / ml / pcs, `piece_g` for things sold by count), price per package + currency, nutrition per 100 g, purine level, red-meat flag, barcode, `matches` (ingredient names it covers). `save_product` upserts by id, barcode, or name + brand.
- Weekly list (`week_start` = Monday in the user's time zone): plan = recipes × servings, meal templates × times, free foods → merged by ingredient name → matched to products → minus pantry → whole packages (unmatched: rounded up to 50 g) → estimated cost. Regenerating replaces only unbought plan lines. `warnings`: weekly red meat / short rib over the caps in `rules/params.py`, high-purine products, per-100 g sat fat / sugar / sodium above the FSA "high" lines (`grocery/params.py`).
- Ticking a line adds it to the pantry (unticking takes it back); a paid price updates the product price per package.
- API (scope `nutrition`): `GET/POST /v1/users/{user}/grocery/products`, `PATCH/DELETE …/products/{id}`, `GET …/list?week=&pantry=`, `POST …/list/generate`, `POST …/list/items`, `PATCH/DELETE …/list/items/{id}`, `GET/PUT …/pantry`. Today page: 饮食 → 采购 (`web/static/grocery.js`).

### Diet profile 「我的饮食档案」 (`assistant/diet_profile.py`, migration 285; issue #32)
Tools: `get_diet_profile` (read, scope memory), `update_diet_profile` (write, runs directly — not a delete).
- Part of the profile card: sections are `assistant_profile` items `diet_targets` (steps, water, note), `diet_rationale` (goal weight, checkpoints), `diet_constraints` (rule + basis), `diet_day_plan` (meals, staples), `diet_adjust_rules` (when → action), structured in the new `data` column; `value` is a short text rendering for `get_memory` / `get_briefing`. A text edit of such an item (`update_profile_card`, `PUT …/memory/profile/{key}`) clears `data`.
- Version log `diet_profile_versions`: `update_diet_profile` with `changes` (+ `reason`) appends a dated entry; version auto +0.1 (`V1.0`, `V1.1`…) or given (`V3.0`).
- Computed on read, never stored: goals (`assistant/diet_goals.py`: #31's versioned goals when that module provides `current_goals`, else SparkyFitness `goal_for_date` over the next 7 days), 28-day average basal / active / total energy from `daily_metrics`, daily deficit and expected weekly change (7700 kcal/kg, flagged above 1 % of body weight per week; sources in `assistant/diet_profile_params.py`).
- API: `GET /v1/users/{user}/diet-profile[?brief=true]` (scope memory; the goals block needs nutrition and the energy block metrics, otherwise null and listed in `hidden`). Today page: one collapsed line at the top of 饮食, tap → sheet with collapsible blocks, version log collapsed (`web/static/diet-profile.js`, open state in localStorage).

`get_profile` now also returns the user's local `now_local` and weekday (the butler uses it to decide "which day the small hours belong to"); `get_training_log` gives each workout an `id`.
`run_tool` runs a tool inside a savepoint: on error only what the tool had half-written is rolled back, and a failed call is still audited (the MCP server commits even after an error).

### Token-lean tools (`docs/ai-assistant-plan.md` section 9.13)
- `get_briefing` (read, scope profile; every other section checked against its own scope, unshared ones listed in `hidden`): one ~1.5k-token opening summary — now, profile, latest scores + the last 7 days (with bed–wake), 7-day vs 60-day means, 28-day training summary + last 7 days, today's reminders, status card, the key profile-card items (health constraints, injuries, current plan, goals; others listed by key), recent observations, banned / caution exercises (`assistant/briefing.py`). The caller's own briefing is cached in process per user: reused while (local date, data fingerprint of the tables it reads) is unchanged and younger than 10 minutes; any write tool of that user drops it; family views are never cached.
- Tool results sent to a model (MCP and in-page chat) go through `assistant/compact.py`: null / empty fields left out, lists of 3+ objects as `{"cols": [...], "rows": [[...]]}`, floats rounded, timestamps to the minute, no spaces. `run_tool` itself still returns the full Python objects.
- Large read tools return a summary by default and the old full shape with `detail=true`: `get_memory`, `get_reminders` (no evidence), `get_exercise_rules`, `get_training_calendar` (no arguments = the last 28 days), `analyze_journal` (only items with a result), `get_cardio`, `get_training_log` (sets as text), `get_daily_metrics` (pivoted by metric); `get_scores` without `details` leaves out `hrv_kind` / `hrv_night_ln` / `hr_max` / `algo_version`; `list_recipes` is one flat row per recipe.
- Schemas: the strict form (every property required, nullable = not given) stays for the Claude API's strict tools; MCP `tools/list` sends a relaxed copy (`toolspec.relaxed`: nullable fields, `user`, `detail` optional, no `additionalProperties`), and `run_tool` fills what was left out (`toolspec.fill_defaults`).

## AI integration layer: each user's own AI (`src/body_engine/ai/`, design in `docs/ai-assistant-plan.md` section 9)
- **Three ways to connect**: ① Subscription (`claude_plan_mcp`, `codex_plan_mcp`, `gemini_plan_mcp`, `generic_mcp_client`) → the user connects the remote MCP `/mcp` from their own official client (Claude Code / Claude Desktop, Codex, Gemini CLI / Antigravity…), and the backend never touches the account; ② API key (`anthropic_api`, `openai_api`, `gemini_api`, `openai_compatible`: DeepSeek, Qwen, Ollama) → in-page chat in the Today page, where the backend calls with this user's own key (Google AI Studio Free Tier keys can tick the $0 unit-price option); ③ the deployer's own body butler (Claude Code Remote Control + MCP), or, opt-in, the owner-only `gemini_cli` in-page adapter that runs the server's signed-in `gemini` CLI (off unless `BODY_GEMINI_CLI_ENABLED=1`; see `docs/ai-assistant-plan.md` 9.14).
- **Isolation**: providers, keys, AI tokens, conversations and usage are all per user_id; the endpoints can only manage your own (family `shares` do not include AI); `gemini_cli` exists only when the admin sets `BODY_GEMINI_CLI_ENABLED=1` and only for `BODY_ASSISTANT_USER_ID` (default 1), so nobody else can use the server's Google sign-in; keys are stored encrypted with AES-256-GCM (`crypto.py`, master key `secrets/ai_master_key`, associated data bound to user_id, so A's ciphertext copied under B cannot be decrypted), only the last 4 characters are returned, and decryption happens only inside this user's own chat requests; an AI token (scope `mcp`) works only on `/mcp` and is not accepted by ordinary endpoints or web login.
- **Master key**: `uv run body-engine ai-key-init` (generates `secrets/ai_master_key` with mode 600, an existing one is left alone). Inside the container it is mounted by compose as a docker secret at `/run/secrets/ai_master_key` (`BODY_AI_MASTER_KEY_FILE`). **Losing the master key = everyone has to re-enter their keys** (`secrets/` is in the backup).
- **AI token**: generated in the Today page under "Me → AI settings → Connect a client (MCP)", or with `uv run body-engine ai-token-create --user-id N --client claude-code [--read-only]`; `ai-token-list`, `ai-token-revoke --user-id N --token-id M`.
- **Connecting to the remote MCP** (address `BODY_PUBLIC_URL` + `/mcp`, inside the tailnet https://your-server.your-tailnet.ts.net/mcp; keep the token in the keychain and use the environment variable `BODY_ENGINE_MCP_TOKEN`, do not write it into a config file):
  - Claude Code: `claude mcp add-json --scope user body-engine '{"type": "http", "url": "<address>/mcp", "headers": {"Authorization": "Bearer ${BODY_ENGINE_MCP_TOKEN}"}}'` (single quotes: the config stores the literal `${…}`, which is only expanded at run time)
  - Codex CLI: `codex mcp add body-engine --url <address>/mcp --bearer-token-env-var BODY_ENGINE_MCP_TOKEN`
  - Gemini CLI / Antigravity: `gemini mcp add --scope user --transport http -H 'Authorization: Bearer ${BODY_ENGINE_MCP_TOKEN}' body-engine <address>/mcp` (or add `{"body-engine": {"type": "http", "url": "<address>/mcp", "headers": {"Authorization": "Bearer ${BODY_ENGINE_MCP_TOKEN}"}}}` to `mcpServers` in `~/.gemini/settings.json`; in Antigravity enter the same address and header in its MCP settings)
  - Once connected, have the AI read the prompt `butler` first (the provider-neutral persona `ai/system_prompt.md`).
- **Chat loop** (`chat.py`): system prompt = `ai/system_prompt.md` + this user's profile and long-term memory (fixed when the conversation starts and never changed afterwards: prompt caching and Claude's preserved thinking require the history to be append-only); the local time is prepended to each user message; read tools run directly, write tools first send `confirm` and wait for the user to tap; the monthly budget (`monthly_budget_usd`, default $5, by calendar month in the user's time zone; skipped when unit prices are $0 or `needs_key=False`) is checked before each model call, and `ai_usage` is recorded; audit `assistant_audit.channel = api:<kind>`, with `provider_id` and `model`. One message makes at most 8 model calls in a row; one conversation holds at most 160 messages.
- **Adapters** (`adapters/`): `anthropic_api.py` (Messages API streaming, default claude-opus-5-5, effort medium, automatic prompt caching, refusal fallbacks="default"), `openai_api.py` (OpenAI uses the Responses API, store=False; compatible endpoints use Chat Completions + the base_url the user enters, http allowed only for the local machine), `gemini_api.py` (google-genai, automatic function calling turned off, `cached_content_token_count` split into `cache_read_tokens`), `gemini_cli.py` (opt-in, owner-only: headless `gemini -o stream-json` as a text generator with a `<tool_call>` protocol; every CLI tool denied by an admin policy, no extensions / MCP servers, fresh temp workspace, allowlisted environment without keys or secrets, prompt via stdin, 180 s kill), `fake.py` (for tests). The price table is in `catalog.py` (unknown models are estimated at the most expensive tier; a custom unit price can be set on the provider).
- **Tests**: `tests/test_ai.py` (separate database `body_test_ai`, fake adapter, no paid API calls): keys do not leak, A's and B's configs are invisible to each other, ciphertext is bound to the user, a conversation uses only its own key and own memory, read-tool loop + audit, write operations need confirmation (nobody else can confirm), rejection and "ignore it and just send a new message", read-only login, images, budget rejection, free-tier $0 unit price, subscription redirect (including `gemini_plan_mcp`), `gemini_cli` off by default + owner-only + adapter tests against a fake `gemini` binary, remote MCP (token scope, read-only, revocation, can only see your own data, audit channel).

## Layout
- `src/body_engine/migrations/`: SQL executed once in numbered order; the table definitions are authoritative here
- `src/body_engine/queries.py`: functions that read data, shared by the API and the AI assistant
- `src/body_engine/importers/`: importers for the full Apple Health export, iOS Shortcut and Open Wearables
- `src/body_engine/ow_client.py`: OW API client (standard library only)
- `src/body_engine/scores/`: the scoring engine (see above)
- `src/body_engine/insights/`: WHOOP-comparable analysis (see above)
- `src/body_engine/sparky_client.py`: read-only SparkyFitness client (workout logs, exercise library, workout templates and weekly plan, meals and targets, weight)
- `src/body_engine/records/`: health records (supplements, lab results, journal and journal analysis, events, exercises, exercise ID mapping): reads/writes, API, assistant tools, migration
- `src/body_engine/rules/`: the rule reminder engine (see above)
- `src/body_engine/goals/`: bedtime target (see above)
- `src/body_engine/training/`: training history (workouts import, merging with SparkyFitness, intensity, calendar endpoints and assistant tools)
- `src/body_engine/assistant/`: the AI assistant (tool registry, authentication + audit, MCP server; tools for scores, training/nutrition/weight, health records and so on; the body butler's SparkyFitness writes `sparky_write.py`, screenshot metrics `snapshots.py`, long-term memory `memory.py` / `memory_api.py` / `memory_seed.py`)
- `src/body_engine/ai/`: the AI integration layer (provider configuration and encryption, AI tokens, remote MCP, in-page chat in the Today page, per-vendor adapters, the provider-neutral persona)
- `src/body_engine/web/`: the Today page (`session.py` cookie login, `views.py` aggregated data, `api.py` endpoints and static files, `static/` PWA)
