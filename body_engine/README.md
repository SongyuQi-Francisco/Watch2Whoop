# Body Engine

The in-house part of the body management system: daily metrics, sleep, scores, journal, supplements, lab results, events, rule reminders, AI assistant. Multi-user (every table has a `user_id`, each person has their own tokens, and viewing someone else's data needs a `shares` grant). For the design see sections 6, 7, 12 and 13 of `../docs/system-design.md`.

## Running
```bash
# From the repository root: start the database and the API (http://127.0.0.1:8100, docs at /docs)
docker compose up -d --build

# In body_engine/: command line (connects to 127.0.0.1:5433, password read from ../secrets/body_db_password)
uv run body-engine migrate
uv run body-engine user-add --name NAME [--role owner] [--birth-date 2001-06-15] [--height-cm 178]
uv run body-engine token-create --user-id 1 --name PURPOSE   # the plaintext is shown only this once
uv run body-engine import-apple-export --user-id 1      # run health_sync/parse_export.py first
uv run body-engine import-shortcut --user-id 1          # archive/health_*.txt uploaded by the iOS Shortcut (new files only; --all re-imports everything) → shortcut_samples etc., format in ../docs/shortcut-sync-spec.md
                                                        # --rebuild-since 2026-10-01: recompute the Shortcut's days from shortcut_samples and re-choose every daily metric since then
                                                        # (each source's daily value is kept in daily_metric_sources; cumulative = largest complete source, spec §5)
uv run body-engine ow-link --user-id 1                  # create the matching user in Open Wearables (just shows it if it already exists)
uv run body-engine import-ow --user-id 1                # incrementally pull daily metrics, sleep and workouts from OW; --full recomputes everything, --start/--end pick the dates
uv run body-engine import-workouts --user-id 1          # pull only OW's workouts → workouts (all history by default; for backfill / recompute after changing training/params.py)
uv run body-engine compute-scores --user-id 1           # sleep / recovery / strain / muscular load → daily_scores (recomputes everything from the scoring start date, about 20 s; --start/--end only limit which days are written)
                                                        # afterwards it also computes body age (weekly, healthspan_weekly) and stress for the last 90 days (stress_daily), about 30 s in total
uv run body-engine sparky-link --user-id 1 --key-name owner  # connect SparkyFitness: validates secrets/sparkyfitness_api_key_owner_ro (must be a read-only key)
uv run body-engine sparky-migrate --user-id 1 --dry-run     # #252: copy food / weight / workouts from SparkyFitness into own tables and check per table; --confirm writes (owner confirms the dry run first)
uv run body-engine import-records --user-id 1           # backfill supplements, lab results, events, exercises and journal from body-management.md, then print a check table
uv run body-engine journal-init --user-id 2             # create the default journal items for a family member (existing ones are left alone)
uv run body-engine link-exercises --user-id 1           # write SparkyFitness exercise IDs into exercise_meta.app_exercise_id (--dry-run only shows the mapping table)
uv run body-engine fetch-exercise-db [--images]          # download the pinned free-exercise-db JSON (+ ~1,750 demo images, ~110 MB) into BODY_MEDIA_DIR (default <repo>/media); idempotent
uv run body-engine seed-exercises [--free-db | --free-db-json PATH] # seed exercise_catalog: curated bilingual overlay + free-exercise-db merged by name / alias (Training V2, issue #41)
uv run body-engine seed-exercises [--free-exercise-db PATH] # seed exercise_catalog from curated bilingual exercises + optional free-exercise-db JSON (Training V2)
uv run body-engine exercises-import-opengym [--dry-run] [--report PATH] # import openGym exercise text (pinned commit, text only, MIT / AGPL-3.0 per row) into exercise_catalog; idempotent; run after seed-exercises (#248, ../docs/exercise-library-opengym.md)
uv run body-engine exercises-media-fetch [--dry-run]     # download the licensed demo pictures (wger, Everkinetic; high-confidence matches in training/media_matches.json) with their credits into exercise_catalog.media; idempotent (#248, ../docs/exercise-library-quality.md)
uv run body-engine static-bundle-pack --out DIR [--since N] # write the versioned static data bundle (exercise library, labels, glossary, split templates) for the app: bundle-v<N>.json.gz + manifest.json; GET /v1/static-bundle?since=N serves the delta (#248, ../docs/static-data-bundle.md)
uv run body-engine evaluate-rules --user-id 1           # rule reminders → reminders (today by default, --date to choose; runs after compute-scores every day)
uv run body-engine hourly-batch --workers 3          # the hourly job for ALL users in one process (import-ow → compute-scores 3 days → evaluate-rules; --full = nightly; --steps, --user-id, --no-skip; docs/hourly-batch.md)
uv run body-engine ow-watch                            # one round of the API's poller: users who uploaded to OW lately and went quiet → import + recompute queued for sync-refresh-run (runs every 30 s inside the API; BODY_OW_WATCH=off disables; ../docs/hourly-batch.md)
uv run body-engine sync-broken                         # read only: users whose phone sync to OW stopped (> 36 h) while they still use the app (sync/broken.py; the Today page shows them 「手机同步已断开」 with a reconnect button)
uv run body-engine notice-send --user-id 7 --title 标题 --body 正文 [--link watch2whoop://sync --link-label 打开]   # one-time message sheet on that user's Today page (notices/; notice-list / notice-revoke; HTTP: /v1/admin/notices for BODY_ADMIN_USER_IDS)
uv run body-engine set-sleep-goal --user-id 1 --bedtime 00:00   # bedtime target (moves earlier step by step starting from the last 7 nights' average; --wake / --pace / --step-days optional)
uv run body-engine nutrition-goals-import --user-id 1   # backfill nutrition goal versions from the SparkyFitness weekly goal plans (active + inactive; idempotent; dry run, --apply writes)
uv run body-engine nutrition-sugar-backfill --user-id 1 --start 2026-09-01 --end 2026-10-21   # sugar / fiber grams written in old entry notes → food_entry_extras (dry run, --apply writes)
uv run body-engine memory-init --user-id 1 --from-md    # the body butler's initial profile card + status card + the "fixed breakfast" template (transcribed from the database + body-management.md; only fills what is missing)
uv run body-engine recipes-init --user-id 1             # recipe metadata: fill in the 25 dishes migrated into SparkyFitness according to body-management.md (existing ones are left alone)
uv run body-engine memory-review-run                    # long-term memory review (#113 phase 2): refresh the review state behind the briefing reminder and delete archived entries older than 90 days, for every user the flag memory_hygiene is on for (the nightly job runs it)
uv run body-engine briefing-stats [--days 7] [--json]   # get_briefing calls, cache hit rate and size in characters per day (counts only; table briefing_stats, #78)
uv run body-engine refresh-status --user-id 1           # recompute the automatically computed items of the status card (the hourly job runs it; the Today page also refreshes it on read when older than 30 minutes)
uv run pytest                                           # each database test uses its own body_test_* database (rebuilt every time); skipped if it cannot connect
```
All imports are idempotent and can be re-run. Source priority is `ow` > `apple_export` > `shortcut`.
For OW's deployment and API key see `../deploy/open-wearables/README.md` (the key is read from `../secrets/open_wearables_api_key`, the address is `BODY_OW_URL`, default http://127.0.0.1:8200).
The OW importer's rules (cumulative metrics de-duplicated by time window + source priority, the export day itself not written, the XML unit problem) are written at the top of `src/body_engine/importers/ow.py` and in section 10 of the system design.
SparkyFitness (workouts, meals, weight) is not imported; it is read live through its API when needed (`src/body_engine/sparky_client.py`, one read-only key per person; only the body butler's write tools use the read-write key; address `BODY_SPARKY_URL`, default http://127.0.0.1:8300; key directory `BODY_SECRETS_DIR`, default `../secrets`). Why a read-only database role is not used is explained at the top of that file. For deployment see `../deploy/sparkyfitness/README.md`.

## Scores (`src/body_engine/scores/`)
WHOOP-style sleep score, sleep need / sleep debt / sleep performance, recovery score (HRV currently uses SDNN), strain (Edwards TRIMP), CTL / ATL / TSB. For the formulas, parameter values, differences from the design and backfill results see "Implementation notes" in section 7 of the system design.
- The pure functions and parameters (`params`, `sleep`, `recovery`, `strain`, `muscle`) live in the Apache-2.0 package [`packages/openbodyscore`](../packages/openbodyscore/README.md) (issue #115); the files here are aliases of those modules, so `from body_engine.scores import params` keeps working. Change the algorithms there; golden tests (`tests/test_openbodyscore_golden.py`) fail on any changed number.
- `params.py`: all parameters and `ALGO_VERSION` (when you change a parameter that affects results, bump the version, then run `compute-scores`).
- `sleep.py` / `recovery.py` / `strain.py`: pure functions; `inputs.py`: reads `sleep_sessions`, OW raw samples and iOS Shortcut samples (`shortcut_samples`, including ungrouped raw heart rate; falls back to the archive when the table is empty); `engine.py`: day-by-day computation and database writes; `store.py`: reads scores (shared by the API and the assistant).
- One row per day; a score that cannot be computed is left empty, with the reason in `flags` (`{code: explanation}`), and the sub-scores and baselines in `details`.
- Needs OW to be running (to pull raw heart rate etc.); the iOS Shortcut archive is read from `$BODY_HEALTH_DATA_DIR/archive` by default.
- `muscle.py`: muscular load `muscle_load` = Σ reps × weight (kg, a relative quantity) of the working strength sets in SparkyFitness workout logs, details in `details.muscle`; not computed for users who have not connected SparkyFitness (v1.1).

## WHOOP-comparable analysis (`src/body_engine/insights/`)
Body age / pace of ageing, stress, today's strain target, sleep coach, health monitor, sleep details (regularity SRI, efficiency, latency), heart rate zones, VO₂max level, weekly / monthly reports. Item-by-item mapping in `../docs/whoop-feature-map.md`; the algorithms, literature, anchor points, API fields and real-data results are in "Body age and other analyses" in section 7 of the system design.
- `healthspan_params.py`: all curve parameters of body age and their sources (bump `ALGO_VERSION` when you change them); `healthspan.py` pure functions (both re-exported from `openbodyscore`, except the tips texts `TIPS` / `tip()`; the pure part of `stress.py` likewise); `healthspan_store.py` reads data, takes weekly snapshots, writes / reads `healthspan_weekly`.
- `stress.py` (writes `stress_daily`), `coach.py` (strain target, sleep coach, health monitor, computed on demand), `sleep_detail.py`, `fitness.py`, `reports.py`; `views.py` holds the read functions shared by the API and the butler tools, `api.py` the routes, `tools.py` the butler tools, `jobs.py` the parts compute-scores runs along the way (a failure in one does not affect the scores).
- The sleep coach uses the bedtime target of the rules session (`goals/`): if that module is present it recommends according to the target, otherwise only according to sleep need.
- Tests: `tests/test_insights.py` (formula edge cases, insufficient data, time zones), `tests/test_insights_db.py` (test database body_test_insights, created if missing, emptied every run).

**Using it on the iPhone**
1. Open Tailscale on the iPhone and check it is connected.
2. Open https://your-server.your-tailnet.ts.net in Safari.
3. In a Mac terminal run `pbcopy < secrets/body_engine_token_web` (the web-only token, user 1), then long-press the token input on the iPhone → "Paste" (the Universal Clipboard of the same Apple ID; Bluetooth and Handoff must be on for both the Mac and the iPhone). Tap "Log in" (「登录」).
4. Add to the Home Screen: Safari bottom "Share" → "Add to Home Screen" → "Add". When opening from the Home Screen you have to **log in once more** (the Home Screen app and Safari have separate cookies).

## Gradual rollout and A/B tests (`src/body_engine/rollout/`, migration 530; guide in `docs/rollout.md`)
- **Feature flags**: keys declared in `rollout/registry.py`, state in `feature_flags` (`off` / `cohort` / `percent` / `all`; percent by a stable sha256 bucket of key + user_id, the cohort always included). `flags.enabled(conn, user_id, key)` (cached 30 s per process), `Depends(flags.require(key))` for endpoints (404 when off), `flags.guard()` elsewhere. `/v1/web/me` and `GET /v1/users/{user}/flags` return the keys on for the user and their A/B variants; the Today page reads them through `window.BodyFlags.on(key)` / `.variant(key)`.

Base version: `body-engine flags consent-base [--set V | --clear]` (default: the text's version, i.e. the behaviour before flags).
- **Experiments** (`experiments`, `experiment_exposures`): `body-engine experiments start <key> --variants control:50,new:50 [--cohort beta] [--days N] | stop | list | results`; stable variant per user, exposures per user and local day (no content), results = users and exposures per variant; outcome metrics plug into `experiments.METRICS`.
- `body-engine flags list | set <key> --state … [--cohort] [--percent N] [--min-consent V|none] | audit`; every change is written to `rollout_audit` (`--by` names who).

## Raw watch data and cardio (`src/body_engine/rawdata/`, `cardio/`, migration 150)
Plan and evidence: `../docs/raw-data-plan.md`. Tables `heartbeat_series` (one row per Apple HRV reading: beat times + our RMSSD / SDNN), `ecg_recordings` (int16 µV waveform, zlib, Apple's classification, R peaks), `workout_hrr` (heart rate recovery after each workout).
```bash
uv run body-engine raw-slim --file export.xml --out raw.zip          # Mac: 700 MB export -> ~0.7 MB zip with only HRV beats + ECG (name / birth date removed)
uv run body-engine import-raw --user-id 1 --file raw.zip             # heartbeat_series + ecg_recordings only, idempotent (also works on the full export)
uv run body-engine hrv-compare --user-id 1 --out ../health_data/reports/hrv-compare.md   # SDNN vs RMSSD recovery, computes only (personal data: keep out of git)
```
- `rawdata/hrv.py` (alias of `openbodyscore.hrv`): RR from beat times, drops gaps / < 300 or > 2000 ms / > 25% from the series median; RMSSD needs ≥ 20 clean successive differences. Recomputed SDNN vs Apple's SDNN: r ≈ 0.9 on about 2,000 real readings from one person.
- The admin history import (`import-apple-zip`) reads the beat lists and `electrocardiograms/*.csv` in the same pass. App copies (below) replace export copies of the same readings (HealthKit has full-precision beat times).
- Scoring: HRV kind per user (#117, `scores/hrv_kind.py`): `scores/params.HRV_KIND` = `sdnn` is the default for everyone; `rmssd` (heartbeat_series only) only for a user switched on with `body-engine hrv-kind --user-id N --enable-rmssd` (table `score_settings`, migration 670; no row = off) **and** with enough beat data (`RMSSD_COVERAGE_DAYS` / `RMSSD_MIN_NIGHTS` / `RMSSD_MAX_GAP_DAYS`; once on RMSSD, an upload gap does not switch back). Never mixed: a partial run (hourly job, `--start`) keeps the stored kind, only a full `compute-scores` (nightly) switches and rewrites the whole history. An RMSSD user's night without beat data gets `hrv_missing` and no recovery. `daily_scores.hrv_kind` and `details.hrv_kind` record the kind; `ALGO_VERSION` is unchanged (the kind tells the two apart). `body-engine hrv-kind --user-id N` (no switch) prints the rule's inputs. Switch a user only after they have read `hrv-compare`.
- `cardio/hrr.py`: HRR60 = peak in the last 2 min of a workout − heart rate 60 s after the end; valid only if the peak ≥ 75% HRmax. Written by `compute-scores` for the days it writes (from the raw heart rate it already loads).

**Types the app reads itself** (`rawdata/hk_types.py`, the registry; `rawdata/quantities.py`, migration 675): the HealthKit
types the Open Wearables SDK cannot read (stand time, exercise minutes, time in daylight, physical effort, sleeping wrist
temperature, environmental / headphone sound, walking heart rate, stair speed, walking steadiness) come as
`quantities[{type, unit, items[{uuid, start, end, value, source}]}]` in the same `POST /v1/ingest/healthkit`. The registry
row of each type (HealthKit id, metric name, unit, `sum` / `avg`, plausible range) decides everything: raw samples go to
`hk_samples` (deduplicated by UUID, `deleted[]` honoured), and each changed (type, local day) is made again with the Apple
Health export import's definitions and written to `daily_metric_sources` as source `app` (`resolve_daily` picks; `app`
ranks first for non-cumulative types). A unit other than the registry's rejects the batch (422). Sleeping wrist
temperature also feeds the scores as raw samples (`scores/inputs.load_app_db`). Changed days queue the score recompute
from the earliest of them (`sync/refresh.queue_scores`, done by `sync-refresh-run`). The app keeps the same registry
(`apps/watch2whoop/lib/src/hk_types.dart`); `tests/test_sync_center.py` checks both match. Emergency stop: flag
`app_types_pause` (on = nothing stored, `metrics_enabled: false`, the app keeps its anchors).

**Sync engine, step S1** (flag `apple_sync_engine`, `rawdata/engine.py`, migration 690, design
`docs/apple-sync-engine.md` §3.2, #219): the app's own HealthKit sync engine uploads through the same endpoint. The
registry is `rawdata/hk_types.ENGINE_TYPES` (every type it reads: HealthKit id, Body Engine name, kind, read unit ×
`factor` = stored unit, `raw` / `stats` upload, aggregation, plausible range, background frequency, order, page sizes); the
app ships it as `apps/watch2whoop/assets/healthkit_types.json` = `python -m body_engine.rawdata.hk_types`, and
`tests/test_apple_sync_engine.py` compares the two. New optional batch fields, columnar (UTC seconds; one entry per
sample in each list; `src` indexes `sources[]`): `sources[]` → `hk_sources`; `samples[]` (quantities), `categories[]`
(e.g. sleep stages, value = HealthKit integer), `workouts[]` (statistics, events, metadata) → `hk_samples`, deduplicated by
UUID; `stats[]` 15-minute UTC-aligned buckets of cumulative types → `hk_stats` (the sent span is replaced); `range` +
`range_done` (re-sync of a date range: stored samples of the range's types inside it, received before the range started
and not sent again, are removed); `runs[]` (sync rounds, counts only) → `sync_runs`; `phase`, `tz` → `rawdata_uploads`.
With the flag on, `deleted[]` also removes engine samples. Changed (type, local day) pairs are queued in `hk_dirty_days`
for the derivation step (S2); the direct-upload types above keep their behaviour (daily value remade at once, score
recompute queued, stopped by `app_types_pause`). The body may be gzip (`Content-Encoding: gzip`, ≤ 2 MB on the wire,
≤ 16 MB decompressed). `GET` (and every `POST` answer) carries `engine: {enabled, mode (ow / shadow), accepts, encodings,
types, limits}`; the app sends only what it lists. Flag off = engine fields refused with 409 `engine_disabled`; a type not
taken now = 409 `type_paused`; engine batches are rate limited per user (batches per minute, bytes per UTC day; more for
the `backfill` / `range` phases): 429 + `Retry-After`. Nothing is stored on 409 / 422 / 429. An older app is not affected.

**Sync engine, step S2** (`rawdata/derive.py`, parameters and sources `rawdata/params.py`, no migration; design §3.2.3–3.2.5):
`uv run body-engine hk-derive-run [--user-id N] [--max-days N]` takes the queued `hk_dirty_days`, oldest first, one
transaction per day (row-locked, a per-user advisory lock; 240 s per run, the rest stays queued; users without consent

quantity types into `daily_metric_sources` (`avg` = mean / min / max / count of the day's raw samples, `sum` = the day's

session rule and stage clean-up, then `importers/ow.sleep_segments` + `common.sessionize`), and workouts
(`training/importer.parse_app`: OW's activity → type table `training/params.HK_WORKOUT_ACTIVITIES` /

days are recomputed. **Sync mode** (`rawdata/engine.mode`, D4): in `shadow` (and `ow`) the derived values are stored
but take no part — `resolve_daily` skips them and is not re-run, no `sleep_sessions` are written, app workouts are
stored with `excluded = 'shadow'` — so no daily value and no score changes; in `app` (reserved for the cut-over S5,

## Training history (`src/body_engine/training/`)
Workouts from the watch / iOS Shortcut and SparkyFitness strength records are merged into one training history, used by the Today page's training calendar and by the body butler when planning training. For the rules, thresholds and backfill results see system design section 16.
- `importer.py`: OW's `/events/workouts` → table `workouts` (migration 080, one copy per source as is, `dup_of` marks duplicates: live sync > export.xml, OW > iOS Shortcut); pulls OW raw heart rate for the workout window to compute TRIMP and minutes in five zones (same method as the scores module), and separates active energy from the energy samples (OW's `calories_kcal` is total energy; the XML's is kJ). `import-ow` runs it every time (the hourly job), idempotent.
- `shortcut_workouts.py`: `Workout|start|end|type|duration seconds|active energy kcal|average heart rate|max heart rate|source` rows in the iOS Shortcut archive → `workouts` (source=shortcut, de-duplicated against the same workout from OW, OW wins); runs automatically during `import-shortcut`. The format is defined by `../docs/shortcut-sync-spec.md`.
- `history.py`: merges by day (SparkyFitness has no times: strength exercises attach to the longest watch strength workout of the day, cardio such as hill climbing attaches to the watch cardio workout closest in duration and uses SparkyFitness's name; unmatched ones are shown separately), intensity grades rest / light / moderate / hard / max (TRIMP → estimate from average heart rate → strength volume → duration; for strength training the higher of heart rate and volume is used), calendar and single-day detail.
- `params.py`: Chinese type names (walking is written as 「步行 / 爬坡」 "walking / hill climbing": the watch cannot tell treadmill incline, so it does not guess), de-duplication, intensity thresholds and their basis; bump `TRAINING_VERSION` after changes, then run `import-workouts`.
- `api.py` / `tools.py`: the endpoints and the assistant tools `get_training_calendar`, `get_training_day`.
- `hevy_import.py` (rollout flag `hevy_import`, migration 615, issue #161, `../docs/hevy-benchmark.md` §6): a Hevy workout export (CSV, gzipped by the page, ≤ 10 MB) → `workouts` (source=hevy, de-duplicated against a watch copy of the same workout, which keeps the heart rate and shows the Hevy sets) + `training_session_logs` (source=hevy, status imported; the page's own rows are source=page and never touched). ## Health records (`src/body_engine/records/`)
- **Supplements**: status = active (taking) / as_needed / paused / stopped / not_needed (assessed, not needed); `rationale` why it is taken, `advice` the current advice; `journal_key` is the matching journal item (created automatically when a supplement is added).
- **Lab results**: `test_key` is an English key unified across reports (uric_acid, triglycerides, alt…), used to look at trends; `flag` = H / L / abnormal / normal. If a reference range exists the value is compared with it, otherwise the report's flag is used.
- **Events**: `time_precision` = minute / day (stored as 12:00 that day) / approx / month; `resolved_on` the date it got better.
- **Journal**: date = the day the behaviour happened; bool items 1 / 0, number items hold a value; **not recorded = missing, not "no"**. The default journal items are in `records/defaults.py`.
- **Journal analysis (first version)**: did vs did not, comparing the means of next-day recovery score, next-day resting heart rate and next-day ln HRV (SDNN); no result if either "yes" or "no" has fewer than 5 days, marked reliable only with at least 15 days each; intervals are a normal approximation and do not control for load / sleep / day of week. The outcomes are in `OUTCOMES` in `records/analysis.py`.
- **Journal analysis (second version, `regression=true`, #118)**: each outcome also gets `regression`: OLS of the outcome on the behaviour (yes 1 / no 0), controlling for the strain of the behaviour day, the sleep duration of the night before the outcome and the weekday; Newey-West (HAC) standard errors with a 7-day lag (in calendar days); with several items (no key) Benjamini-Hochberg across the items of each outcome (`p_adj`, `significant`, `direction` at FDR 5%). Only days with all covariates are used; at least 5 yes / 5 no days and 20 residual degrees of freedom, else `insufficient`; `collinear` when the behaviour cannot be separated from the weekday / covariates. Standard library only (`records/regression.py`), parameters with sources in `records/analysis_params.py`, method in `docs/scoring-validation.md` §2.2. The first version's fields are unchanged. Today page: flag `journal_regression` (with `records_v2`) switches the Trends 行为影响 card to the adjusted effect.
- **Exercises**: `exercise_ref` is an English slug (upright_row, cable_face_pull…); `app_exercise_id` is the SparkyFitness exercise ID, and `link-exercises` matches automatically by source_id / name / alias (`records/exercise_link.py`, idempotent, filled ones are not overwritten, unmatched ones are listed); to change a single one use `PUT .../exercises/{slug}` or the assistant tool `set_exercise_rule`.
- **Migration**: the data transcription for `import-records` is in `records/md_seed.py` (the 2026-10-16 version of body-management.md); every entry has an `import_key`, so re-running does not duplicate and does not overwrite later changes made in the database.

## Rule reminders (`src/body_engine/rules/`)
Double-progression weight increase / decrease (4.5), calorie adjustment by weekly average weight (5.2), pre-workout eating (4.2.1), red meat / beef short rib frequency cap (5.3.1, 5.3.2), banned / caution exercises (4.3), red recovery score / sleep debt (section 7). For the rules, thresholds, the places where something was inferred and results on real data see system design section 13.
- `params.py`: all thresholds, each with its source; the ones marked "inferred" are values taken from the most conservative reading where body-management.md is unclear. Bump `RULES_VERSION` after changing them.
- `context.py`: reads the data (SparkyFitness with the evaluated user's own read-only key; a source that cannot be read affects only the rules that depend on it); `progression.py` / `nutrition.py` / `safety.py`: the rules, pure functions `(Ctx) -> RuleResult`; `engine.py`: runs all rules and idempotently writes `reminders` (re-running does not duplicate, status is kept, ones no longer valid are deleted, old ones are kept when a rule errors) and `rule_runs`.
- Advice only; it does not change targets, plans or records in SparkyFitness.
- `sugar_caps` (issue #31): today's added sugar over the cap of the goal in effect (default 25 g, WHO < 5% energy) → info, over 50 g (WHO 10%) → warning; more than 2 sugary drinks in a rolling 7 days → warning. Entries without an added-sugar number are not counted (unknown ≠ 0). Calorie adjustment reads the goal in effect from `goals/nutrition.py`.

## Nutrition goals and sugar (`goals/nutrition.py`, `nutrition/`, migration 290, issue #31)
**Why Body Engine holds the goals.** SparkyFitness keeps goal presets and ONE active weekly goal plan; `/goals/by-date` only resolves through the active plan (dates before it get the default goal), presets have no added-sugar field, and nothing records who changed a goal or why. So past dates could not be judged against the goal that applied then. `nutrition_goal_versions` is now the source of truth for rules, status cards, reports, adherence, meal suggestions and the Today page; SparkyFitness `/goals/by-date` is only the fallback for dates before a user's first version. Goals are not written back to SparkyFitness (its own app may show older numbers).
- **Version** = `{effective_from, training, rest, training_weekdays, name, reason, set_by, actor_user_id, created_at}`; each set `{calories, protein_g, carbs_g, fat_g, sat_fat_max_g, added_sugar_max_g, fiber_min_g}` (null = no target; no added sugar cap → the default 25 g, `added_sugar_cap_default=true`). Rows are never changed: a change is a new row; fields left null carry over from the version in effect on `effective_from` (default today, up to 366 days back / 90 ahead). The version in effect on a date = greatest `effective_from` ≤ date, newest row first; its training set applies on `training_weekdays` (ISO 1 = Monday … 7 = Sunday), the rest set on the other days. `set_by`: `web` / `api` / `mcp:<client>` / `chat` / `import`.
- **Read API (for the Today page diet card and other modules)**: `GET /v1/users/{user}/goals/nutrition?date=` →
  `goal` (that date's resolved goal: `{date, source: body_engine | sparkyfitness | null, version_id, effective_from, day_type: training | rest, name, calories, protein_g, carbs_g, fat_g, sat_fat_max_g, added_sugar_max_g, added_sugar_cap_default, fiber_min_g}`),
  `version` (the version in effect with both sets), `upcoming` (versions starting after `date`), `history` (every version, newest effective date first; `superseded=true` = replaced by a later row with the same date, never in effect). In Python: `goals.nutrition.resolver(conn, user_id)(day)`, `current()`, `history()`, `view()`.
- **Backfill**: `body-engine nutrition-goals-import --user-id N [--apply]` turns every SparkyFitness weekly goal plan (active and inactive, `GET /weekly-goal-plans` + `/goal-presets`) into a version: `effective_from` = plan start, the preset with more calories = training set, its weekdays = `training_weekdays`; idempotent per plan (`import_key`).
- **Sugar per entry** (`nutrition/extras.py`): `log_food`, meal template items and recipe ingredients take optional `sugar_g`, `added_sugar_g`, `fiber_g`, `sodium_mg` (null = unknown; added ≤ total ≤ carbs) and `log_food` also `sugary_drink`. Sugar / fiber / sodium are written into the SparkyFitness food (`sugars`, `dietary_fiber`, `sodium`); added sugar has no SparkyFitness field, so every value also goes to `food_entry_extras` (keyed by the entry id; SparkyFitness values win when both exist). Sugary drinks: the flag, else name keywords minus "无糖 / zero / diet" (params in `rules/params.py`). `update_food_entry` carries an entry's extras to its new id / date (scaled by the portion; dropped when it becomes another food). Old entries: `nutrition-sugar-backfill` parses 「添加糖 12g」 / 「含糖 30g」 / 「纤维 3g」 from notes (never overwrites log_food values).
- **Daily totals** (`nutrition/daily.py`, used by `get_nutrition`, `/today`, rules, status card, reports): per day calories / macros, `sugar_g` / `added_sugar_g` / `fiber_g` / `sodium_mg` summed over the entries that know them (null when none do), `known: {of, sugar_g, added_sugar_g, fiber_g, sodium_mg}` (how many entries knew each), `sugary_drinks`, `goal` (in effect that day) and `adherence: {calories, protein}` (calories within ±10 %, protein ≥ 90 % of that day's goal; null when not logged). Entries carry the same four fields and `sugary_drink`.
- **Reports**: `current.nutrition` / `previous_values.nutrition` in `/reports`: logged days, average calories / protein, days on target for calories / protein (each day against its own goal), added sugar average over days with numbers, days over the cap, sugary drinks, goal names used.

## Bedtime target (`src/body_engine/goals/`)
Set a desired bedtime and it moves earlier step by step starting from the average bedtime of the last 7 nights (by default 20 minutes every 3 days), computing tonight's target, progress and the expected date of reaching it; the rule `sleep_goal` gives daily "go to bed before what time tonight" with a pre-bed routine, consecutive deviations, and stage achievement. Across midnight it works by "sleep day" (a night belongs to the evening before bedtime, so 06:30 is 6.5 hours later than 00:00). Details, the basis of the parameters and the API fields are in system design section 13.1.
- `params.py`: pace, tolerance, the times of the pre-bed routine and their basis (body-management.md 6.2); `sleep.py`: pure computation; `store.py`: reading/writing the table `sleep_goals` and the views; `api.py` / `tools.py`: endpoints and assistant tools.

### Status card (`assistant/status.py`, table `assistant_status`, migration 070)
Each item: `key`, `label` (≤ 6 characters), `value` (≤ 12 characters, **without the unit**), `unit` (nullable), `tone` (good / warn / bad / neutral), `trend` (up / down / flat / null), `good_direction` (up / down / null: which direction of the trend is good), `group` (身体 body / 目标 goal / 健康 health / 训练 training / 作息 routine / 饮食 diet / 其他 other; the list is ordered by this and then by sort), `spark` (values from old → new, at most 30, may contain null; null if none), `note` (≤ 20 characters, nullable), `updated_at`, `source` (auto / assistant / seed).
| auto item | Algorithm |
|---|---|
| `weight` (体重, body weight) | Latest weigh-in (manual SparkyFitness weigh-ins first, same as the Today page); trend = mean of the last 7 days vs the previous 7 days; tone: weekly mean down 0.3–1.0kg good, down > 1.0 or up > 0.3 warn; spark = the last 30 weigh-ins |
| `to_goal` (距目标, distance to goal) | Latest weight − the `goal_weight` written by the butler; note estimates the number of weeks at the current weekly pace |
| `recovery` (恢复, recovery) | Mean recovery score of the last 7 days (≥ 67 good, 50–66 neutral, 34–49 warn, < 34 bad), trend vs the previous 7 days; spark 14 days |
| `sleep_debt` (睡眠债, sleep debt) / `sleep_hours` (睡眠时长, sleep duration) | The latest sleep debt (≤ 1h good, ≤ 2h warn); mean actual sleep over the last 7 nights (≥ 7h good, ≥ 6h warn); spark 14 days (hours) |
| `bedtime` (入睡时间, bedtime) | Mean onset time of the main sleep over the last 7 nights (≤ 00:30 good, ≤ 02:00 warn, later bad); spark = hours relative to midnight (23:30 = −0.5, 02:40 = 2.67) |
| `uric_acid` / `alt` / `triglycerides` | The latest lab result ("high 520"), more than 20% over the upper limit bad; spark = values of all past results |
| `training_week` (本周训练, training this week) | Number of days with workout records in the last 7 days (≥ 4 good, 2–3 warn); spark = the last 6 windows of 7 days |
| `red_meat_week` (红肉 7 天, red meat 7 days) | Same definition as the rule engine (journal red_meat_g first, otherwise estimated from food names; "红肉 Ng" (red meat N g) in a name is taken as labelled) |
| `added_sugar_today` (今日添加糖) / `added_sugar_7d` (7 天平均) | Added sugar today over the entries that know it (未知 when none do; ≤ cap of the goal in effect good, ≤ 50 g warn, more bad); 7-day average over the days with numbers, spark 7 days |
An item that cannot be computed (no data) is deleted; if reading the data fails the last value is kept and the reason is recorded in the cursor of `sync_state` (source=status_auto).

### Recipes (`assistant/recipes.py`, table `recipe_meta`, migration 090; design in system design section 15)
Tools: `list_recipes`, `get_recipe`, `suggest_meals` (read); `create_recipe`, `update_recipe`, `log_recipe` (write, ask for confirmation).
- Nutrition is computed from ingredients (ingredients store the quantities of the whole pot; one serving = total ÷ servings); `constraint_flags` = `{purine_mg, purine_level, sat_fat_g, sat_fat_level, red_meat_g, short_rib}` (per serving; thresholds in `assistant/recipe_params.py`: purine < 150mg low, ≤ 350mg medium; saturated fat ≤ 4g low, ≤ 7g medium; one copy is stored on write and recomputed with the current thresholds on read).
- Automatic tags: high protein (≥ 30g per serving), low purine (low and no red meat), low saturated fat, quick (prep + cook ≤ 20 minutes), red meat, includes staple.
- Logging: one SparkyFitness food entry "dish name (N servings, red meat N g)", meal_logs keeps one row (recipe_id), and `last_cooked_on` is computed from entries that have not been undone.
- Suggestions: the target for this meal = the day's target (SparkyFitness, by date) − what is already logged; earlier main meals with no records are assumed eaten at the usual proportions (breakfast 25%, lunch 35%, dinner 35%), and what remains is divided proportionally between this meal and the later main meals (snacks at most 10% of the day); dishes that exceed the weekly red meat allowance or include beef short rib eaten in the last 7 days are excluded; scoring by calorie deviation, protein shortfall, purine (×1.5 when uric acid is high), saturated fat, eaten in the last 2 days, favourite, whether you can make it; a dish without staple counts as served with 90g of rice at lunch and dinner.
- When created / renamed / ingredients changed, a copy is synced to SparkyFitness (custom food `recipe:<id>` + meal); an error there does not affect Body Engine.
- Shopping preparation: ingredients carry `purchase_unit` (purchase-unit hint) and `store` (costco / woolworths / other, left empty for now).

In-page chat: `ai_providers.web_tools` (off by default) turns on the vendor's own web search / fetch for Anthropic, OpenAI and Gemini API keys. ### Diet constraints, per user (`nutrition/constraints.py`, migration 450; issue #76)
Every diet limit is the user's own; the code holds no one's limits. A user without constraints is not limited, penalised or excluded anywhere.
- Kinds (`nutrition/constraint_params.py`, with literature reference values the AI may suggest): `red_meat_g_per_week`, `red_meat_meals_per_week`, `food_times_per_week` (+ `target` food, aliases), `low_purine`, `low_saturated_fat`, `avoid_alcohol`. Each row has a basis (出处) and `effective_from`; a change closes the row in effect and adds a new one, so the rows are the version history.

Budgets (core, each group, meta, MCP list ≤ 35k, each page) and a summary-size cap for every read tool on synthetic data are in `tests/test_tool_groups.py`; the numbers in `ai/params.py`.
- **Scene context tools and playbooks** (issue #100, `docs/ai-assistant-plan.md` section 9.18): `get_training_context` (this week's plan, readiness and load, banned / caution exercises, the last 14 days, training days and equipment) and `get_week_review_context` (7 days of recovery, sleep, load, stress, training, food adherence, weight, journal and events vs the week before; the weekly report's numbers) return everything a task needs plus `rules` (guardrails) and `needs` (what is missing), sections authorized by shares like `get_briefing` (`assistant/scenes.py`). Playbooks in `ai/playbooks/*.md` (`plan_shopping`, `plan_training_week`, `weekly_review`, `log_meal_from_photo`; AI-facing, Chinese) are served as MCP prompts next to `butler` and by `get_playbook(name)`, the same text. All three tools are in the core group and in the fallback AI's whitelist.

## AI integration layer: each user's own AI (`src/body_engine/ai/`, design in `docs/ai-assistant-plan.md` section 9)
- **Three ways to connect**: ① Subscription (`claude_plan_mcp`, `codex_plan_mcp`, `gemini_plan_mcp`, `generic_mcp_client`) → the user connects the remote MCP `/mcp` from their own official client (Claude Code / Claude Desktop, Codex, Gemini CLI / Antigravity…), and the backend never touches the account; ② API key (`anthropic_api`, `openai_api`, `gemini_api`, `openai_compatible`: DeepSeek, Qwen, Ollama) → in-page chat in the Today page, where the backend calls with this user's own key (Google AI Studio Free Tier keys can tick the $0 unit-price option); ③ the deployer's own body butler (Claude Code Remote Control + MCP), or, opt-in, the owner-only `gemini_cli` in-page adapter that runs the server's signed-in `gemini` CLI (off unless `BODY_GEMINI_CLI_ENABLED=1`; see `docs/ai-assistant-plan.md` 9.14).
- **Isolation**: providers, keys, AI tokens, conversations and usage are all per user_id; the endpoints can only manage your own (family `shares` do not include AI); keys are stored encrypted with AES-256-GCM (`crypto.py`, master key `secrets/ai_master_key`, associated data bound to user_id, so A's ciphertext copied under B cannot be decrypted), only the last 4 characters are returned, and decryption happens only inside this user's own chat requests; an AI token (scope `mcp`) works only on `/mcp` and is not accepted by ordinary endpoints or web login.
- **Master key**: `uv run body-engine ai-key-init` (generates `secrets/ai_master_key` with mode 600, an existing one is left alone). Inside the container it is mounted by compose as a docker secret at `/run/secrets/ai_master_key` (`BODY_AI_MASTER_KEY_FILE`). **Losing the master key = everyone has to re-enter their keys** (`secrets/` is in the backup).
- **AI token**: generated in the Today page under "Me → AI settings → Connect a client (MCP)", or with `uv run body-engine ai-token-create --user-id N --client claude-code [--read-only]`; `ai-token-list`, `ai-token-revoke --user-id N --token-id M`.
- **Connecting to the remote MCP** (address `BODY_PUBLIC_URL` + `/mcp`, inside the tailnet https://your-server.your-tailnet.ts.net/mcp; keep the token in the keychain and use the environment variable `BODY_ENGINE_MCP_TOKEN`, do not write it into a config file):
  - Claude Code: `claude mcp add-json --scope user body-engine '{"type": "http", "url": "<address>/mcp", "headers": {"Authorization": "Bearer ${BODY_ENGINE_MCP_TOKEN}"}}'` (single quotes: the config stores the literal `${…}`, which is only expanded at run time)
  - Codex CLI: `codex mcp add body-engine --url <address>/mcp --bearer-token-env-var BODY_ENGINE_MCP_TOKEN`
  - Antigravity (Google AI Pro / Ultra, or its free tier): `agy mcp add --header "Authorization: Bearer ${BODY_ENGINE_MCP_TOKEN}" body-engine <address>/mcp` (the shell fills in the token; Antigravity does not expand `${…}` in its config), or `{"mcpServers": {"body-engine": {"serverUrl": "<address>/mcp", "headers": {"Authorization": "Bearer <token>"}}}}` in `~/.gemini/config/mcp_config.json` (`serverUrl`, not `url`); then `chmod 600` that file
  - Gemini CLI (paid Gemini API key only: since 2026-06-18 it no longer serves AI Pro / Ultra sign-ins): `gemini mcp add --scope user --transport http -H 'Authorization: Bearer ${BODY_ENGINE_MCP_TOKEN}' body-engine <address>/mcp`
  - The Gemini web / mobile app's custom MCP apps (Connected Apps) need OAuth (dynamic client registration) and are US-only; `/mcp` only takes Bearer tokens today (`docs/ai-assistant-plan.md` 9.15)
  - Once connected, have the AI read the prompt `butler` first (the provider-neutral persona `ai/system_prompt.md`).
- **Chat loop** (`chat.py`): system prompt = `ai/system_prompt.md` + this user's profile and long-term memory (fixed when the conversation starts and never changed afterwards: prompt caching and Claude's preserved thinking require the history to be append-only); the local time is prepended to each user message; read tools run directly, write tools first send `confirm` and wait for the user to tap; the monthly budget (`monthly_budget_usd`, default $5, by calendar month in the user's time zone; skipped when unit prices are $0 or `needs_key=False`) is checked before each model call, and `ai_usage` is recorded; audit `assistant_audit.channel = api:<kind>`, with `provider_id` and `model`. One message makes at most 8 model calls in a row; one conversation holds at most 160 messages.
- **Adapters** (`adapters/`): `anthropic_api.py` (Messages API streaming, default claude-opus-5-5, effort medium, automatic prompt caching, refusal fallbacks="default"), `openai_api.py` (OpenAI uses the Responses API, store=False; compatible endpoints use Chat Completions + the base_url the user enters, http allowed only for the local machine), `gemini_api.py` (google-genai, automatic function calling turned off, `cached_content_token_count` split into `cache_read_tokens`), `fake.py` (for tests). The price table is in `catalog.py` (unknown models are estimated at the most expensive tier; a custom unit price can be set on the provider).
- **Tests**: `tests/test_ai.py` (separate database `body_test_ai`, fake adapter, no paid API calls): keys do not leak, A's and B's configs are invisible to each other, ciphertext is bound to the user, a conversation uses only its own key and own memory, read-tool loop + audit, write operations need confirmation (nobody else can confirm), rejection and "ignore it and just send a new message", read-only login, images, budget rejection, free-tier $0 unit price, subscription redirect (including `gemini_plan_mcp`), the retired `gemini_cli` (not in the catalog, old rows can only be deleted), remote MCP (token scope, read-only, revocation, can only see your own data, audit channel).

## Self-service sign-up (`src/body_engine/account/`, migration 230)
Design, mail provider setup and deploy steps: [`docs/self-signup-plan.md`](../docs/self-signup-plan.md).
- Sign-in without passwords: e-mail + one-time 6-digit code (`account/signin.py`, mailer `account/mailer.py`: SMTP or `console`)
  and native Sign in with Apple (identity token verified against Apple's JWKS, audience `BODY_APPLE_AUDIENCES`).
- New accounts are `pending` (403 `account_pending` everywhere except `/v1/account*`, `/v1/web/me`) until they redeem an
  invite code (`account/invites.py`; `body-engine invite-code create | batch | list [--kind referral] | revoke`; `create --uses N`
  = one code for N people, each redemption bound to the account's sign-in identities, one redemption per identity ever;
  `create --code TEXT` = a readable code such as a channel name, 4–40 letters / digits, not 12 or 16 long).
  User referral codes (migration 350, on with `BODY_REFERRALS_ENABLED=1`, default off): Me → 邀请好友 shows the user's own
  code, a share link `/app/?invite=CODE` (pre-fills the invite step) and how many joined (`GET /v1/users/{user}/invite-code`);
  limits in `account/params.py` (10 friends, 3 per 24 h, no expiry); a disabled / deleted inviter's code stops; each
  redemption records the inviter and a pending `invite_rewards` row. Redemption activates the account and
  provisions it in the background (`account/provision.py`: OW user, SparkyFitness account + encrypted keys, journal items,
  profile card); `body-engine provision-run` retries unfinished ones (hourly) and removes pending accounts after 7 days.
- Existing accounts (admin-created) sign in with e-mail / Apple once an identity is bound (`account/identities.py`):
  `body-engine identity-link --user-id N --email x [--move] | --list | --unlink`, `user-add --email`, `activation-code create
  --email`; signed-in users add more under Me → 「登录方式」 (`web/static/identities.js`, `POST /v1/account/identities/email`
  with a code, `/v1/account/identities/apple` with an Apple token from the app). A pending sign-up that enters an existing
  account's activation / login code on the invite step moves its identity there. Apple joins an existing account only on
  an Apple-verified, non-relay e-mail equal to exactly one active account's bound e-mail. Changes are audited in
  `identity_events` (migration 390).
- `DELETE /v1/account` (Today page Me → 删除账号) deletes the account and its data in Body Engine, OW and SparkyFitness (`account/delete.py`).
- Tests: `tests/test_account.py` (fake JWKS, console mailer, fake OW / SparkyFitness).
- Provisioning retries (`account/provision.py`, migration 785): transient errors (connection refused, timeout, HTTP 5xx)
  are tried 3 times within a run; a failed run writes every failing step with its exception type to
  `user_provisioning.last_error` and sets `next_attempt_at` (10 min doubling per attempt, at most 6 h); `provision-run`
  only picks due rows, and one user's failure never stops the others.

## Running it on a small server (memory, logs; `docs/api-memory.md`)
- Run jobs and checks as `body-engine <command>` in a **separate** container with its own memory limit, never with
  `docker exec` into the API container: each CLI process is ~75 MB inside the API's limit, and the kernel then kills the
  biggest process there, the API.
- `BODY_SYNC_IMPORT=queue`: "sync now" (`POST /v1/users/{user}/sync/refresh`) only queues the OW import; the per-minute
  `sync-refresh-run` imports and recomputes (default: import in a thread of the API process).
- `BODY_LOG_DIR=<dir>`: the API's log (warnings, tracebacks; no access lines) also goes to `<dir>/engine-YYYY-MM-DD.log`,
  kept `BODY_LOG_KEEP_DAYS` (14) days. `compose.yaml` mounts `health_data/ops/engine/`.
- Responses carry `X-Body-User: <id>` of the authenticated user (`obs.py`): log it in the reverse proxy
  (`$upstream_http_x_body_user`) and hide it from clients (`proxy_hide_header X-Body-User`).
- The image sets `MALLOC_ARENA_MAX=2` (fewer glibc arenas for the API's thread pool).

## Optional plugins (`src/body_engine/plugins.py`)
None by default. Set `BODY_PLUGIN_DIR` to a directory of plugin packages (`<dir>/<name>/__init__.py`, name `[a-z][a-z0-9_]*`) to extend a deployment without changing this code. A plugin may define:
- `router` (a FastAPI `APIRouter`, included as is; reuse `records.api.current_user` for authorization);
- `JOBS = [Job(name, fn, every_s=300)]` or `Job(name, fn, daily_at="08:00", tz="Australia/Sydney")`: run inside the API process with a Postgres advisory lock and their own connection; must be idempotent (a daily job may run again after a restart);
- `migrations/*.sql`: applied by `body-engine migrate` after the core migrations, recorded as `<name>/<file>`;
- `page_scripts(conn, user)` / `page_styles(conn, user)`: files under `<name>/static/` the Today page loads for this user (only listed files are served, at `/app/plugins/<name>/<file>`; `/app/plugins/manifest.json` lists them).

The Today page loads the listed files before initialising `window.BodyPlugins` and offers `window.BodyHooks.on(name, fn)`: `"page"` (`{page}`, when the visible page changes) and `"action"` (`{feature, page}`, when a control is used; `feature` is the control's `data-feature`, id or data-attribute name, never typed text or record values). `body-engine plugins list | run <plugin> <job>`. Also `"sheet"`: `{open: true, kind, key}` when a detail sheet opens (`kind` `"card"` = opened from an element marked `data-card="<key>"`, `"explain"` = a metric explanation, `"lab"` = a lab test's history; other sheets have no key) and `{open: false}` when it closes. `data-card="<key>"` marks a data card on a page with a fixed code key (lower-case `[a-z0-9_.:-]`, never record values) so a plugin can see which cards are on screen.

## Notifications and push (`src/body_engine/notify/`, migration 630, issue #175)

One entry point for every feature: `notify(conn, user_id, kind, title, body, url=None, data=None)`
(`from body_engine.notify import notify`). It writes an in-app notification in the caller's transaction and, unless
the push is off, pushes to the user's registered iPhones through APNs from a background thread.

- `kind` is `<category>.<event>` (e.g. `circle.like`, `circle.comment`); categories are declared in `notify/params.py`
  (`CATEGORIES`, unknown ones raise) and are what users switch on / off. `title` / `body` are a string (Chinese) or
  `{"zh": …, "en": …}`; the push uses the recipient's language, the list the page's. `url` is a path of the Today page:
  `/app/#tab=friends` switches the tab, `/app/#notifications` opens the list, every link is also the window event
  `body:link` (detail = the hash parameters, e.g. `{tab: "friends", post: "9"}`). `data` stays on the server
  (`data.actor_id` counts people when merging).
- No push (only in-app) when: the rollout flag `notifications` is off for the user (`flag_off`), the category is off
  (`off`), quiet hours (`quiet`, default 23:00–07:00 in the user's time zone), no device (`no_device`), or the server
  has no APNs key (`no_key`). The decision is stored in `notifications.push_status`.
- Merging: the same kind to the same person within 30 minutes while unread is one notification on the phone
  (`apns-collapse-id` = kind), its text a count ("3 个人给你点了 ❤️"); only the first one makes a sound, at most 10
  updates per window. Texts per kind in `params.MERGED`.
- Devices: the app registers its APNs token (`POST /v1/users/me/push-devices`), only for itself; a token moves to
  whoever registers it last; sign-out (`POST /v1/account/logout` or `DELETE /v1/users/me/push-devices`) removes it;
  tokens Apple reports as invalid (410, BadDeviceToken, …) are removed; a token only valid in the other environment
  (sandbox / production) is retried there once and corrected.
- APNs: token-based auth over HTTP/2 (`notify/apns.py`): `BODY_APNS_KEY_FILE` (the .p8, a secret file), `BODY_APNS_KEY_ID`,
  `BODY_APNS_TEAM_ID`, `BODY_APNS_BUNDLE_ID`. Check after deploying: `body-engine notify status`,
  `body-engine notify test --user-id N` (pushes now, ignoring quiet hours and settings). `notify prune --days 90`.
- In-app API (behind the flag): `GET /v1/users/me/notifications`, `/notifications/unread`, `POST /notifications/read`,
  `GET / PUT /notification-settings`. Today page: `web/static/notify.js` (bell in the header, list, settings; in the app it
  asks for push permission on the first visit to the Friends tab or the settings).
- Tests: `tests/test_notify.py` (fake APNs client, never Apple).

## Circles and circle sharing (`src/body_engine/friends/`, migration 470)
Design: [`docs/friends-social-plan.md`](../docs/friends-social-plan.md). **Behind the feature flag `friends`** ([`docs/rollout.md`](../docs/rollout.md)): while it is off for someone, every `/v1/friends/*` endpoint answers 404, the Today page draws no circle entry, and circle grants (`shares.circle_scopes`) do not count unless the flag is on for **both** people (`auth.granted_scopes`); hand-made grants never depend on it. Turn it on with `body-engine flags set friends --state cohort --cohort beta --min-consent 2026-10-22.2`. The Today page part is 「我 → 圈子」 (`web/static/circles.js`); opening `/app/?circle=CODE` shows the join sheet after sign-in.
| Endpoint (acts for the caller only; changes need write) | Description |
|---|---|
| `GET /v1/friends` | My circles (members, `my_scopes`, for the owner the number of live invite codes), invites addressed to me (from a referral sign-up), the scope choices and defaults, `consent_ok` |
| `POST /v1/friends/circles {name, scopes}` | New circle, I am owner and first member; returns the first invite code (plaintext only here) |
| `PATCH /v1/friends/circles/{id} {name}` · `DELETE /v1/friends/circles/{id}` | Owner: rename / dissolve |
| `POST /v1/friends/circles/{id}/invite {reset, days, permanent}` | Owner: a new code valid `days` (1 / 3 / 7 / 30, default 3; `permanent: true` = never expires; anything else → 400; `reset: true` first revokes every live code); at most 5 live codes. Returns `{id, code, expires_at}` (null = never) |
| `DELETE /v1/friends/circles/{id}/invites/{invite_id}` | Owner: revoke one live code early (the owner's circle view lists the live codes with `expires_at` and `used_count`, never the plaintext) |
| `GET /v1/friends/invite?code=` | What a code opens (name, owner, member count) |
| `POST /v1/friends/join {code \| invite_id, scopes}` | Join with the scopes I pick; joining twice changes nothing |
| `PATCH /v1/friends/circles/{id}/me {scopes}` · `DELETE /v1/friends/circles/{id}/me` | Change what I share / leave (an owner who leaves hands over to the longest-standing member) |
| `DELETE /v1/friends/circles/{id}/members/{user}` · `DELETE /v1/friends/invites/{id}` | Owner removes a member / I decline an invite |
| `GET /v1/friends/overview` | Friends tab cards (`friends/cards.py`): `me` (with `received` cheers) and `members[]` (`circles`, `shared`, `scores` {recovery, zone, label, sleep_min, strain, synced_today, last_date, week[7]} or null, `trained` or null, `hidden`, `sent` cheers today) |
| `GET /v1/friends/leaderboard?board=body\|activity\|lifestyle\|recomp\|longevity` | One board (`friends/leaderboard.py`, weights / windows / thresholds with sources in `friends/params.py`): `rows[]` {id, display_name, self, status ok \| not_shared \| insufficient, score 0–100, rank, sub}; ranked rows first (ties share a rank), the others after with no rank. Scores are against each person's own baseline / goals; a person's numbers are cached 10 minutes per local day |
| `POST /v1/friends/nudges {to, kind}` | 👏 `clap` / 💤 `sleep` / 💪 `train`: only to someone sharing a circle with me, once per kind per person per day (409 after) |
- Sharing: a member's scopes (`friends/params.py` `CIRCLE_SCOPES`; defaults scores, sleep, training, `nutrition_summary`) are shown to every other member. Between two people the union over all common circles goes to `shares.circle_scopes`, separate from the hand-made `shares.scopes` (which alone obeys `expires_at`); `auth.can_view` and `/v1/web/me` use both. Every membership change recomputes it in the same transaction, so leaving / removal / dissolving take effect at once and never touch hand-made grants.
- `ecg` is never a circle scope (rejected by the API, a CHECK on `circle_members.scopes` and `shares.circle_scopes`). `nutrition_summary` = whether calories / protein met the goal; a `nutrition` grant implies it (`auth.IMPLIED_BY`).
- Creating / joining needs consent version `friends/params.py` `CONSENT_VERSION` (2026-10-22.2, the first with the circle clause) or later (409 otherwise). Wrong invite codes: 10 per 15 minutes per IP and per user, then 429. Only code hashes are stored.
- Referral sign-ups (#57): redeeming a user's referral code invites the new user to every circle the inviter owns (30 days, `invite_redemptions.circle_id` = the first); nothing is shared until they accept and pick scopes. Account deletion leaves every circle first (`store.leave_all`), so owned circles pass on.
- Leaderboards (Friends tab → 排行榜): body (recovery + sleep performance, 7 days), activity (acute:chronic workload ratio + training days; needs scores + training), lifestyle (on-time bedtime vs the person's bedtime goal or own median + nutrition goals met; needs sleep + nutrition_summary), recomp (weight / body fat toward the person's goal weight + strength volume vs own 28-day mean + protein met; needs weight + training + nutrition_summary), longevity (4 weeks: change of the body-age gap + pace of aging). Food days are the 7 finished days (ending yesterday). SparkyFitness being unreadable makes a row "insufficient", never fails the board.
- AI tool `get_friends_overview` (read-only, no arguments): each circle member's shared status, 7-day recovery and board ranks, with what they do not share listed; not in the fallback AI's tool set.
- Tests: `tests/test_friends.py` (cross-user access, leaving, ECG, hand-made grants, consent, limits, referral, deletion, cards, cheers, every board, the AI tool).
- **Circle activation codes and avatars (#199, migration 655, no feature flag)**: `friends/codes.py`, `friends/admin.py`, `images/`. A readable code (matched ignoring case, spaces and dashes) bound to one circle, with `max_uses` (new accounts only: existing accounts join without taking a place, also once it is used up), an optional expiry and `disable` (both stop everyone); every use is a row in `circle_code_uses` (`new_account` or an existing one). In the sign-up invite step (`POST /v1/account/redeem-invite`, tried before the other kinds of codes) it activates the account and keeps a place in the circle; the person joins with the circle's default scopes only after the consent (`POST /v1/users/{user}/consent` → `circles_joined`; `GET /profile` → `circle_pending` for the consent sheet). On the Friends page (`GET /v1/friends/invite`, `POST /v1/friends/join`) an existing account joins with the scopes it picks. No new-account places left (new accounts only) / disabled / expired → 410, circle full → 409. The code row is locked for the whole redemption, so concurrent sign-ups never exceed `max_uses`. Circle avatars: `GET /v1/friends/circles/{id}/avatar` (members only); `images/store.py` accepts PNG / JPEG / WebP, crops to 256×256 WebP and drops all metadata. CLI: `body-engine circle-admin create | avatar | list`, `body-engine circle-code create | list | uses | disable` (docs/admin-guide.md). Tests: `tests/test_circle_codes.py`.

## Layout
- `src/body_engine/migrations/`: SQL executed once in numbered order; the table definitions are authoritative here
- `src/body_engine/queries.py`: functions that read data, shared by the API and the AI assistant
- `src/body_engine/importers/`: importers for the full Apple Health export, iOS Shortcut and Open Wearables
- `src/body_engine/ow_client.py`: OW API client (standard library only)
- `src/body_engine/scores/`: the scoring engine (see above)
- `src/body_engine/insights/`: WHOOP-comparable analysis (see above)
- `src/body_engine/sparky_client.py`: read-only SparkyFitness client (workout logs, exercise library, workout templates and weekly plan, meals and targets, weight)
- `src/body_engine/ownstore/`: own tables for food, food library, weight and workout logs that replace SparkyFitness (issue #252, migration 735, `docs/own-food-weight-storage.md`): mapping from SparkyFitness rows, dual write behind the rollout flag `own_food_store` (off = unchanged), `sparky-migrate` with a per-table check; nothing reads them yet (phase 3)
- `src/body_engine/records/`: health records (supplements, lab results, journal and journal analysis, events, exercises, exercise ID mapping): reads/writes, API, assistant tools, migration
- `src/body_engine/rules/`: the rule reminder engine (see above)
- `src/body_engine/goals/`: bedtime target (see above)
- `src/body_engine/training/`: training history (workouts import, merging with SparkyFitness, intensity, calendar endpoints and assistant tools)
- `src/body_engine/assistant/`: the AI assistant (tool registry, authentication + audit, MCP server; tools for scores, training/nutrition/weight, health records and so on; the body butler's SparkyFitness writes `sparky_write.py`, screenshot metrics `snapshots.py`, long-term memory `memory.py` / `memory_api.py` / `memory_seed.py`)
- `src/body_engine/ai/`: the AI integration layer (provider configuration and encryption, AI tokens, remote MCP, in-page chat in the Today page, per-vendor adapters, the provider-neutral persona)
- `src/body_engine/web/`: the Today page (`session.py` cookie login, `views.py` aggregated data, `api.py` endpoints and static files, `static/` PWA)
